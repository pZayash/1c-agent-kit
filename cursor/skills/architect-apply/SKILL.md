# architect-apply — архитекторский apply (роль архитектора)

Ты **архитектор** (старшая модель, Опус). Готовишь почву для основного `apply`,
который выполнит **слабая модель-исполнитель**. Цель: дать исполнителю опору
(качественное ядро кода, контракты, снипперты, чёткое задание), чтобы он не
«творил дичь» в проекте. Сам **не тестируешь** результат и **не трогаешь тяжёлый
XML** — экономишь контекст и токены. Результат исполнитель вернёт тебе на ревью
по протоколу [review-request](../review-request/SKILL.md) / [review](../review/SKILL.md).

**Парные скиллы:**

- [openspec-apply-change](../openspec-apply-change/SKILL.md) — обычный полный
  apply одной моделью. `architect-apply` — фаза **перед** ним: ядро + задание,
  остальное доделывает исполнитель.
- [review-request](../review-request/SKILL.md) / [review](../review/SKILL.md) —
  канал возврата работы исполнителя и твой вердикт.

## Когда вызывать

- Change крупный/рискованный, и его доделку отдают слабой модели.
- Нужно «задать рамки и качество», а механику (метаданные, формы, печать) отдать
  линейному исполнителю.
- Явные триггеры: «архитекторский apply», «дай обвязку исполнителю», «каркас под
  слабую модель».

Если задачу делаешь сам целиком — это [openspec-apply-change](../openspec-apply-change/SKILL.md),
не этот скилл.

## Аргументы

`/architect-apply <change|slug> [scope] [exec]`

- `<change|slug>` — имя OpenSpec change (он же `slug` треда ревью на шине).
  Если не задан — вывести из контекста; при неоднозначности
  спросить одним вопросом (`openspec list --json`).
- `scope` (необязательно) — пользовательская подсказка по объёму: `full` (Опус
  делает почти всё), `core` (ядро + задание), `min` (минимум кода, упор на
  задание). По умолчанию Опус **выбирает сам** (см. ниже).
- `exec` (необязательно) — компетентность исполнителя: `junior` (больше опоры,
  подробные снипперты), `mid` (контракты + указания). Влияет на детальность
  задания.

## Граница работ

### Объём — адаптивно, Опус судит

Объём кода, который пишешь сам, **обратно** масштабируется со сложностью/ценой
контекста change:

- **Тривиальный/малый** change → можно сделать почти всё (кроме стоп-зоны ниже).
- **Крупный/дорогой по контексту** → только переиспользуемое **ядро**
  (общие модули, алгоритмы, граничные случаи) + детальное задание; массовое и
  механическое (метаданные, формы, повторяющийся перенос) — исполнителю.

Пользователь может переопределить объём (`scope`) и указать компетентность
исполнителя (`exec`). Своё решение по объёму **зафиксируй** в `executor-task.md`
(раздел «Разделение работ») и, если отступаешь от `tasks.md`, в
`implementation-notes.md`.

### Стоп-зона — НЕ трогать никогда

Чтобы не жечь контекст/токены и не ломать тяжёлые артефакты:

- **Тяжёлый XML**: `Form.xml`, XML метаданных объектов (`*.xml` справочников/
  документов/перечислений), MXL-макеты. Их создаёт/правит исполнитель скиллами
  `meta-*`/`form-*`/`mxl-*`.
- **Тесты и БД**: прогон тестов, загрузка в dev/prod-ИБ, отладка, smoke. Всё —
  исполнителю.

Ты работаешь только с `.bsl`, лёгкими текстовыми правками и **статическими**
проверками (`bsl-check`). Исключение по `.xml` — можешь указать исполнителю
точечные правки (например поднять `<Comment>`), но не выполняешь их сам.

## Шаги

1. **Выбрать change.** `openspec list --json` при неоднозначности. Деградация:
   если активного change нет — работай по свободной задаче, `slug` возьми из
   контекста или спроси. Объяви: «architect-apply по change: `<name>`».

2. **Прочитать контекст.** `openspec instructions apply --change "<name>" --json`;
   прочитать `contextFiles` (proposal/design/specs/tasks). Без change — задачу/
   обсуждение из чата.

3. **Решить объём** (адаптивно, с учётом `scope`/`exec`). Назвать вслух, что
   пишешь сам и что отдаёшь исполнителю.

4. **Написать ядро.** Качественный `.bsl` по стандартам проекта (префикс `яя_`,
   локалы с малой буквы, параметры `п-`, комментарий модификации по `MODIFICATION_COMMENT_TEMPLATE`, doc-комментарии).
   Создавать только `.bsl` (оболочку `.xml` общего модуля делает исполнитель).
   После каждого модуля — `bsl-check` через `bash tools/sandbox/run.sh` до **OK**.

4a. **Code-as-spec для ядра.** Написанные архитектором экспортные методы SHALL
    нести REQUIREMENT-блоки над сигнатурой (формат: `// СПЕЦИФИКАЦИЯ` →
    `// REQUIREMENT: REQ-NNN — ...` → prose → `// VERIFIED-BY: ...`). Если есть
    связанный prose spec в `openspec/specs/<cap>/spec.md` — перенести prose в
    анкер. Если speки нет, но метод значимый — создать новый REQUIREMENT с
    `(no-test)`. MODULE_CONTRACT в шапку модуля (если ещё нет). Маркер
    `<!-- render -->` в spec.md добавляет apply, не трогать здесь.

5. **Зафиксировать решения** в `openspec/changes/<name>/implementation-notes.md`
   (только при отступлениях/решениях на месте — гейт как в
   [openspec-apply-change](../openspec-apply-change/SKILL.md)). Контракты колонок,
   неявные допущения, закрытые open questions.

6. **Отметить сделанное** в `tasks.md`: `[ ]` → `[x]` по кодовым задачам, что
   реально выполнил. Метаданные/формы/тесты оставить исполнителю.

7. **Написать задание** `openspec/changes/<name>/executor-task.md` по шаблону
   ниже.

8. **Передать исполнителю.** Выдать пользователю:
   - короткую сводку (что сделано, bsl-check статус, что отдано);
   - **готовый промпт** для исполнителя (copy-paste), указывающий читать
     `executor-task.md` и вернуть результат скиллом `review-request <slug>`.

9. **Ждать возврат.** Исполнитель пишет заявку `/review-request`
   (`handoffs/<slug>/rN-request.md`). Ты разбираешь скиллом
   [review](../review/SKILL.md) → `rN-result.md`.

## Шаблон executor-task.md

Файл `openspec/changes/<name>/executor-task.md`. Разделы:

1. **Заголовок + роль исполнителя** — «Ты линейный исполнитель; ядро написано и
   проверено; работай по контракту; отступления — в implementation-notes.md».
2. **Контекст** — ссылки на proposal/design/specs/implementation-notes и готовое
   ядро (стабильные артефакты, не копировать).
3. **Контракт ядра** — сигнатуры написанных функций/модулей, что менять нельзя.
4. **Глобальные правила проекта** — префикс, именование, комментарий
   модификации, sandbox для python/bash, `rtk` для git, без `cd`/`git -C`, без
   коммитов без разрешения.
5. **Задачи по группам** — по порядку; для каждой: объект/путь, скилл
   (`meta-*`/`form-*`), валидация. Снипперты-образцы вызовов ядра (детальность по
   `exec`).
6. **Definition of Done** — зелёные `*-validate`, `bsl-check` OK, `<Comment>`
   поднят, перенос/печать работают, чекбоксы в `tasks.md`, отступления в
   `implementation-notes.md`, без коммитов.
7. **Что НЕ делать** — не менять ядро (баг → в notes), не мигрировать прод-данные,
   не трогать CFE без указания, не коммитить.

## Протокол возврата

- Исполнитель завершает: [review-request](../review-request/SKILL.md) `<slug>` →
  заявка `handoffs/<slug>/rN-request.md`.
- Архитектор разбирает → [review](../review/SKILL.md) `<slug>` →
  `handoffs/<slug>/rN-result.md` (находки, ответы, чеклист «что чинить»).
- `slug` = имя change. Канал — тред `handoffs/<slug>/`.

## Guardrails

- Сам не запускаешь тесты, не грузишь в ИБ, не правишь тяжёлый XML.
- Каждый написанный `.bsl` проходит `bsl-check` до OK перед передачей.
- Объём — адаптивно; решение фиксируешь в `executor-task.md`.
- Не коммитить без явного разрешения пользователя.
- Дрифт требований по ходу — в `implementation-notes.md` (не молча в код), гейт
  малый/структурный как в [openspec-apply-change](../openspec-apply-change/SKILL.md).
- `executor-task.md` и `implementation-notes.md` живут в папке change; задание —
  рабочий артефакт, при архивации не нужен (notes удалить перед archive).
