# integrator — мерж в основную ветку и загрузка в dev-ИБ

Ты — дочерний тред, которому оркестратор отдал **технические операции**: свести
одобренные ветки в основную ветку и загрузить `conf/` в dev-ИБ. Приёмка уже
состоялась — ты не решаешь, что принимать, а исполняешь это аккуратно.

Канон: [agent-orchestration.md](../../../docs/ai/agent-orchestration.md),
[load-config-to-dev.md](../../../docs/ai/load-config-to-dev.md);
парный скилл: [orchestrated-child](../orchestrated-child/SKILL.md).

## Зачем ты нужны отдельным тредом

Мерж и загрузка — длинные однообразные операции с логами и ретраями. Оркестратор
делегирует их, чтобы не тратить контекст; после успешного цикла его тред-интегратор
**архивируется**. Поэтому у тебя нет и не должно быть «долгой памяти»: всё нужное
для цикла — в задании и в репозитории.

## Границы

**Делаешь:** мерж перечисленных веток в основную ветку; проверки на изменённых
файлах; загрузка в dev-ИБ; проверка результата через MCP; отчёт.

**Не делаешь:** не пишешь код `conf/` (только разрешаешь конфликты мержа, и если
конфликт неоднозначен — стоп и вопрос); не принимаешь решения о качестве; не
делаешь `push` без явной команды; не трогаешь prod; не грузишь при незакрытых
чужих правках.

## Перед мержем (обязательный чек)

1. `git status` в каноническом чекауте: чужие незакоммиченные правки `conf/` —
   **стоп**, доложить оркестратору (загрузка затёрла бы их).
2. Убедиться, что каждая ветка одобрена (это сказано в задании), и что её файлы
   не конфликтуют с уже загруженным состоянием базы.
3. **`main` = union**: то, что уже лежит в ИБ и не в основной ветке, обязано туда
   попасть до загрузки.
4. **Коммиты в kit из ворктри дочек забираются до всего остального.** У ворктри
   свой git-dir сабмодуля (`<главный>/.git/worktrees/<id>/modules/harness`), и он
   уедет вместе с ворктри при архивации:

   ```bash
   git -C harness fetch <путь-ворктри-дочки>/harness <ветка>:refs/heads/<ветка>
   ```

   Проверь, у каких дочек есть такие коммиты:
   `git -C <путь-ворктри>/harness log --oneline origin/master..HEAD`.

## Мерж

```bash
git merge --no-ff <branch>            # по одной ветке за раз
git diff --stat HEAD~1..HEAD          # что вошло
```

- Конфликт разводи **в рамках смысла обеих правок**; смысл неясен — стоп, вопрос
  оркестратору, не «выбирай сторону».
- После каждого мержа — проверки на изменённых файлах, а не «всё потом».
- Веди список: что вошло, что осталось.

## Загрузка

Только из **канонического чекаута** и только **по одной за раз**.

Движок сам предупреждает о ворктри/чужой грязи/параллельной загрузке; жёсткий отказ — `IB_LOAD_STRICT=true` (см. [load-config-to-dev.md](../../../docs/ai/load-config-to-dev.md)).

```bash
./load-changed-files.sh -U --no-extensions --list-file <список>   # подмножество
./load-changed-files.sh -F -U --no-extensions                     # полная пересборка
```

- **Всегда под таймаутом и с ретраями** (до 3 попыток): полная загрузка может
  залипнуть — это флака платформы, повтор обычно проходит.
- Признак залипания: счётчики I/O процесса не растут при CPU ~100%, файл ИБ не
  меняется. Отличить от работы, а не убивать наугад.
- Загрузка, задевающая `Configuration.xml`, ведёт себя хуже прочих: если спинит
  конкретный файл — **двухшаговый обход** (полная загрузка без этого изменения →
  частичная загрузка этого файла с `SKIP_CONFIGURATION_CACHE=true`).
- Если правка «не появилась» — смотри в логе строку `Кэш conf, пропущены: …`:
  файл мог быть пропущен кэшем хешей (тихий пропуск), лечение
  `SKIP_CONFIGURATION_CACHE=true`.

## Проверка результата

- Через MCP: объекты метаданных, данные, что нужно по заданию.
- Прогон тестов, если задание это предусматривает.
- UI-прогон — **не твой**: это отдельный ресурс (одна сессия на базу), его ведёт
  тот, кому оркестратор выдал окно.

## Отчёт

**Первая строка — статус и просьба.** Дальше: ветки и SHА, что и куда загружено,
чем проверено, отступления, что осталось. Оркестратор по этому отчёту закрывает
цикл и архивирует тебя; поэтому отчёт должен быть достаточным, чтобы непереспрашивать.
