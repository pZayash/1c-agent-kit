# review — вердикт ревьювера (архитектор)

Ты **ревьювер**. Читаешь заявку исполнителя (`rN-request.md` в ящике), проверяешь
работу, пишешь **вердикт** (`rN-result.md`) в ту же задачу `kind=review`. Это
рабочий канал между двумя сессиями, не спека и не долговременная память.
`handoffs/<slug>/` — не канон.

**Принцип:** ссылаться на устойчивые артефакты (`openspec/`, `memory/`, коммиты,
дифф по маркерам `№%`), не копировать их.

**Парный скилл:** заявку оформляет исполнитель —
[review-request](../review-request/SKILL.md). Этот скилл — только сторона
ревьювера. Не путать роли: тут ты НЕ описываешь свою работу, ты её проверяешь.

**Отличие от [handoff](../handoff/SKILL.md):** `handoff` — generic-снимок сессии;
`/review` — вердикт в двустороннем протоколе с ролями. Термины:
[CONTEXT.md#language](../../../CONTEXT.md#language).

## Когда вызывать

«сделай ревью», «запиши вердикт ревью», «результат ревью в файл», «сохрани
findings» — когда ревьювишь свежую заявку исполнителя (**канал A**: человек в
чате ревьювера, часто с доп. замечаниями).

Субагент Task `reviewer` (**канал B**, default после заявки) — тот же скилл;
запуск по фразам «отправь на ревью» / «запусти reviewer» / «прогони review».
Контракт каналов: [review-protocol.md](../../../docs/ai/review-protocol.md).

Если просят **оформить заявку** («оформи на ревью», «заявка на ревью») — это
другая роль, переключись на [review-request](../review-request/SKILL.md).

## Аргументы

`/review <slug>`

- `<slug>` — единица треда ревью. Имя openspec change, если ревью привязано к
  change; иначе свободный kebab-топик (без даты-префикса). Пример:
  `upd-tnved-rashodnaya`, `forms-web-client-blocker`.
- Если `<slug>` не задан — вывести из контекста; при неоднозначности спросить
  одним вопросом.

## Куда писать

Корень: [mailbox](../mailbox/SKILL.md). Тред = `id`. Искать задачу по `slug`
(`kind=review`) или по claim `inbox/reviewer/<id>`.

- Вердикт: `tasks/<id>/artifacts/rN-result.md` + запись в `artifacts[]`.
- Claim: `inbox/reviewer/<id>` → `processing/reviewer/<id>` (atomic rename).
- Резюме «годен»: `completed`, токен в `archive/reviewer/<id>`.
- «на доработку» / «блокер»: `input-required`, токен в `inbox/<from>/<id>`.
- `handoffs/` не создавать.

**Перед записью** Read целевого md.

### Нумерация раунда

Артефакты `tasks/<id>/artifacts/r*-*.md`:

- `N` = номер последнего `rN-request.md` без парного `rN-result.md`.
- Нет открытой заявки — «нет открытой заявки», предложить указать `id` явно.

## Вход: заявка и замечания оператора

1. Прочитай `tasks/<id>/artifacts/rN-request.md` целиком.
2. Если есть секция «Замечания оператора» — учти в фокусе и в «Ответы на
   сомнения»; устойчивые пункты отрази в находках / «Что чинить» при необходимости.
3. Замечания только в чате (канал A, без правки заявки) — тоже учти; в вердикте
   кратко отметь, что учтены реплики из чата.

Без открытой заявки — стоп (сообщить «нет открытой заявки»), не ревьюить «весь
дифф» наугад.

## Обязательные проверки

При формировании вердикта **обязан** проверить изменения на соответствие
архитектурным правилам проекта (см. `docs/ai/code-standards.md`):

1. **Минимальность правок**: изменения в типовом (вендорском) коде строго
   минимальны.
2. **Инъекции**: правки в типовом коде — через «инъекции» (однострочные вызовы
   `яя_...` или корректировки переменных), основная логика вынесена за пределы
   типовых методов.
3. **Комментарии модификации**: правки в типовых объектах обёрнуты комментариями
   по стандарту (например, `// +{prefix} ... №%<slug> ...` — см. `MODIFICATION_COMMENT_TEMPLATE` в `.env.example`).
4. **Расположение и сортировка методов**: новые методы в правильных `#Область`;
   внутри областей — сначала по логической связанности, затем по алфавиту.
   Проверь, что вставка метода **не разорвала пару doc-коммент↔функция** (коммент
   соседа не оторвался). `#Область яя_` — только в типовых объектах; в наших
   `яя_`-объектах обёртка лишняя (см. `docs/ai/object-conventions.md`).
5. **Именование методов**: без латиницы, только русский.
6. **Чистота change**: `git diff` несёт маркеры **только текущего** slug. Grep
   чужих `№%<другой-slug>` в диффе → блокер (изолировать коммит; `git add -p`).
   Особо — смешанные хунки двух changes в одном методе: развести нельзя, требовать
   переразбивку.
7. **EOL-санитария форков**: `git diff --ignore-cr-at-eol` vs обычный stat —
   расхождение = флип EOL конструктором (форк типовой формы), блокер коммита.
8. **Консистентность семейства**: однотипная доработка на КП/ЗП/РН — единый
   паттерн и точка срабатывания на всех; разнобой без причины → находка.
9. **Размещение кода в типовых модулях** (особое внимание): новый код в типовом
   (вендорском) модуле — преимущественно в области `яя_`. Вне `яя_` — только при
   необходимости (когда инъекция технически обязана стоять в типовом методе) и
   **обязательно** с комментариями модификации по стандарту проекта. Код вне `яя_`
   без обёртки комментариями или без обоснования необходимости → блокер.
10. **Только программные изменения форм**: правки форм — программно (например
    `ИзменитьРеквизиты`, добавление элементов/команд в коде модуля формы).
    Правки `Form.xml` (разметка, реквизиты формы) → блокер. Grep изменённых
    `**/Forms/**/Ext/Form.xml` в диффе → находка 🔴.
11. **Code-as-spec REQUIREMENT-анкеры**: если change затрагивает `яя_`-код в
    `conf/` — каждый новый/изменённый значимый экспортный метод SHALL нести
    REQUIREMENT-блок над сигнатурой (после док-коммента). Проверить:
    - `spec-lint check` зелёный по изменённым файлам (запустить через sandbox)
    - каждый REQUIREMENT привязан к живому методу (нет оторванных анкеров от
      удалённых методов)
    - нет дублей REQ-ID в диффе (два метода с одним ID → 🔴)
    - дрифт требований из `implementation-notes.md` отзеркален в анкеры
    - если capability уже code-as-spec (`<!-- render -->`) — нет prose-only
      Requirement в spec.md без соответствия анкеру (разрешены только Purpose и
      ручные секции)
    Отсутствие REQUIREMENT на значимом методе → 🟠. Дуэли REQ-ID → 🔴.

Нарушения — фиксировать в «Находки» (🔴/🟠) и требовать переделать в «Что чинить».

## Шаблон вердикта (`rN-result.md`)

```markdown
# Вердикт ревью: <slug> — раунд N

**Когда**: YYYY-MM-DD HH:MM (локальное)
**Ревьювер**: <модель/агент>
**Резюме**: годен | на доработку | блокер

## Находки

Формат каждой: метка + `файл:строка` + суть + фикс.

- 🔴 `path:line` — критично: <суть>. Фикс: <как>.
- 🟠 `path:line` — важно: <суть>. Фикс: <как>.
- 🟡 `path:line` — мелочь: <суть>. Фикс: <как>.

## Ответы на сомнения / вопросы заявки

По пунктам «Сомнения автора» и «Открытые вопросы» из `rN-request.md`.

## Диагноз затыка

Только если в заявке был затык: вероятная причина + направление решения.

## Что чинить

Чеклист императивов — исполнитель отчитается в `rN+1-request.md`.

- [ ] <действие>
- [ ] <действие>

## Открытые вопросы

К автору или пользователю. Если нет — опустить.

## Ссылки

- openspec/, memory/, коммиты.
```

После формальной части ревьювер волен дописать свободную прозу, если она
помогает понять контекст.

## Чего не писать

- Полный текст proposal/design/tasks, кода модулей — только ссылки и `файл:строка`.
- Полный дифф — группировка по маркеру `№%`, не построчно.
- Секреты, токены, пароли, содержимое `.env`, строки подключения.
- Длинные дампы MCP/qmd — итог + параметры запроса для повтора.

## После записи

1. Сообщить пользователю относительный путь и объём (строки).
2. Подсказать следующий шаг: «исполнителю: `/review-request <slug>` следующего
   раунда после правок по чеклисту».
3. Кандидаты в долговременную память (повторяющиеся грабли, договорённости) —
   перечислить отдельно; в `memory/` не писать без запроса пользователя.

## Границы

- `/review` не коммитит и не пушит (ящик вне git).
- Не заменяет OpenSpec: контракт/спека меняется в `openspec/**`, вердикт только
  ссылается. Дрифт требований — по
  [openspec-apply-change](../openspec-apply-change/SKILL.md).
- Не дублирует `memory/` и `handoff`.
- Не гонять по ревью-файлам check-bsl.py / xml-wellformed — это не код.
