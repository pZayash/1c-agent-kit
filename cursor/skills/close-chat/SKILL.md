# close-chat — закрытие сессии по чек-листу

Скилл проводит сессию через четыре фиксированных шага в конце работы: убедиться, что нет подвешенных вопросов, заархивировать готовые OpenSpec changes, убрать мусор, закоммитить только то, что было сделано в этом чате.

**Принцип:** быстро прогнать пайплайн с минимумом вопросов. По умолчанию коммитим только то, что трогали в этом чате (touched). Чужие изменения не коммитим — ни целые файлы, ни чужие чанки внутри смешанного файла (partial stage по маркерам `№%`). Вопрос пользователю — **только** если без него нельзя достоверно определить принадлежность файла к сессии или если есть реальный блокер. Сомнение само по себе — не повод спрашивать; если файл уверенно touched — включаем в коммит без вопроса (целиком или partial). Никаких автоматических удалений за пределами явного whitelist.

## Когда вызывать

- «/close-chat», «закрыть чат», «закрытие сессии», «конец чата», «заверши сессию»
- Пользователь явно намекает на финал работы и просит привести репозиторий в порядок перед уходом

Не вызывать автоматически в фоне — это всегда взаимодействие с пользователем.

## Аргументы

- Без аргументов — полный пайплайн интерактивно.
- `--dry-run` — показать план по каждому шагу, ничего не менять и не коммитить.
- `--skip 0|1|2|3` — пропустить указанный шаг (можно повторять: `--skip 0 --skip 2`).

## Подготовка

Перед шагом 0 собрать три списка (использовать дальше во всех шагах):

1. **touched-список** — файлы, которые агент сам создавал/редактировал в этой сессии (по своей памяти о tool calls Write/Edit и созданным untracked). Сюда же — файлы, которые в `git status` появились/изменились в ходе этой сессии и логически связаны с её темой (например, авто-сгенерированные артефакты touched-скриптов). Если файл уверенно touched — относим к touched без вопроса. Помечать «неоднозначно» только если действительно нет признаков принадлежности к сессии.
2. **OpenSpec touched** — поддиректории `openspec/changes/<id>/`, которые тронули в чате.
3. **session-markers** — множество маркеров `№%<change-id>` сессии: по одному на каждый id из OpenSpec touched (например `№%print-faksimile-toggle-group-a`). Канон группировки — [git-workflow.md](../../../docs/ai/git-workflow.md).

Caveman-режим на подтверждениях ослабляется (см. Auto-Clarity skill `caveman`): вопросы и предупреждения писать нормальным русским.

## Шаг 0. Открытые вопросы

Цель шага — поймать реальные блокеры, не превращать его в допрос. Если блокеров нет — одна строка «открытых вопросов нет» и сразу шаг 1.

Источники (просканировать молча):

- TodoWrite-список сессии — пункты `in_progress` / `pending`.
- **Незакрытые OpenSpec changes из touched-списка** — `openspec/changes/<id>/tasks.md` с прогрессом <100%.
- **`operator-checklist.md` из touched OpenSpec changes** — ручные задачи оператора (smoke, проверки в 1С). Файл НЕ парсится openspec CLI и не входит в прогресс tasks.md, но незакрытые пункты (`- [ ]`) — повод спросить оператора. Если файл есть — вывести его содержимое в чат (оператору неудобно открывать файл вручную).
- **`implementation-notes.md` из touched OpenSpec changes** — журнал отклонений от proposal/design ([docs/ai/openspec-implementation-notes.md](../../../docs/ai/openspec-implementation-notes.md)). Прочитать, выделить только **явные** отклонения и нерешённые TODO («отложено», «спайк», «нужно подтвердить», «не решено», расхождения smoke-тестов). Если notes непусты и change близок к archive — напомнить «Разбери разлад» / [`/evolve`](../evolve/SKILL.md) до удаления.
- История чата — только **явно подвешенные** вопросы пользователю, на которые он не ответил.
- **Открытые заявки на ревью** — в **ящике шины** задачи `kind=review` со
  статусом `submitted` / `input-required` (не только старые
  `handoffs/<slug>/rN-request.md`). Слот:
  `python3 /opt/agent-repo/tools/mailbox/paths.py open-reviews`. Хост: тот же
  модуль при `AGENTS_MAILBOX`. Упомянуть как незакрытый тред (id + slug), не
  интерпретировать каждый пункт заявки как вопрос.

Действие:

- Если ничего не найдено — сказать «открытых вопросов нет», шаг 1.
- Если нашлось — собрать **один** компактный список и задать **один** общий вопрос: «по этим пунктам — доделать сейчас / оформить в `/handoff` / архивировать как есть». Без отдельного вопроса на каждый пункт.
- Не интерпретировать каждое упоминание в `implementation-notes.md` как вопрос: если отклонение зафиксировано и не требует решения — упомянуть строкой, не спрашивать.

Не переходить к шагу 1, пока есть нерешённые блокеры из ответа пользователя.

> **Примечание про archive**: `implementation-notes.md` должен быть удалён **до** archive (см. [docs/ai/openspec-implementation-notes.md](../../../docs/ai/openspec-implementation-notes.md)). Это делается на шаге 1 в рамках [openspec-archive-change](../openspec-archive-change/SKILL.md). На шаге 0 файл ещё нужен — не удалять.

## Шаг 0б. Уроки сессии (memory → docs)

Канон: [agent-session-lessons.md](../../../docs/ai/agent-session-lessons.md).

Проверить: были ли в чате **новые или существенно обновлённые** записи
`memory/` по:

1. правке XML `conf/` (метаданные, формы, load);
2. WEB UI-тестированию (`web-test`, гибрид с MCP).

Действие:

- Нет таких записей — одна строка «уроков для переноса в docs нет», шаг 1.
- Есть — **один** вопрос оператору: «Уроки: `<список memory/*.md>`.
  Перенести в `docs/ai/` (какие файлы)?» — да / отложить / нет.
- Агент **не** правит `docs/ai/` без ответа оператора на этом шаге.
- Запись в `memory/` должна была появиться **во время** сессии, не на close-chat
  (close-chat только напоминает про docs).

## Шаг 1. Архивация OpenSpec

Кандидаты — **только touched-changes**, у которых после шага 0 tasks 100%.

**⛔ Блокер-гейт архивации.** Если хотя бы один touched-change НЕ готов к
архивации (tasks <100% **ИЛИ** есть `operator-checklist.md` с незакрытыми
пунктами **ИЛИ** архивация не удалась по технической причине: sync fail,
`implementation-notes.md` не удалён, archive-dir уже существует) — **СТОП**.
Не переходить к шагу 2 (очистка) и шагу 3 (коммит). Задать **один** явный
вопрос оператору с перечислением всех незакрытых change и причин:

> «Не архивировано: `<id>` — tasks N% (незакрыто: M), operator-checklist: K
> незакрытых. Архивировать как есть / доделать / `/handoff` / оставить?»

Дождаться ответа оператора. Только после явного решения по каждому change
(«архивировать как есть» подтверждает архивацию с неполным tasks) — продолжить.

Для каждого change, готового к архивации (или с явным «архивировать как есть»):

1. Sync delta-specs в `openspec/specs/` (правило из [memory/feedback_openspec_always_sync_and_archive.md](../../../memory/feedback_openspec_always_sync_and_archive.md)).
2. Архивировать через скилл [openspec-archive-change](../openspec-archive-change/SKILL.md).
   При `spec-lint render`: **один** процесс; бюджет как в
   [sandbox.md § spec-lint render](../../../docs/ai/sandbox.md) и
   [spec-lint README](../../../tools/spec-lint/README.md) — не плодить фоновые
   `render` при тишине.
3. Сообщить пользователю: что заархивировано, куда переехало.

Changes <100% без подтверждения «как есть» — не трогать, перечислить
«не архивирован: `<id>`, прогресс N%». Если оператор сказал «доделать» —
не архивировать, продолжить работу (close-chat прервать, вернуться к задаче).
Если «`/handoff`» — оформить handoff, не архивировать.

## Шаг 2. Очистка мусора

Сканировать `git status` (untracked + modified) **только по touched-списку**, классифицировать:

| Категория | Действие |
| --- | --- |
| **Whitelist** untracked: `tmp/`, `*.tmp`, `*.bak`, `*.orig`, `scratch_*`, `_tmp_*` | Удалить без вопросов, перечислить после |
| **Touched-черновики**: служебные скрипты, черновики JSON для MCP-запросов, отладочный код, явно созданные «на разок» | Удалить без вопросов, перечислить после |
| **Полезное будущим агентам** (заметки, наработки, незавершённые исследования) | Не удалять — упомянуть строкой, предложить `/handoff` одним вопросом по всему списку |
| **Чужие untracked / modified** (не в touched-списке) | Не трогать, не упоминать пофайлово — одна строка «вне скоупа сессии: N файлов» |

Перед удалением показать итоговый список «удалить:» и подождать **одно общее** подтверждение (либо «да» через `/handoff` — отдельный поток). На `--dry-run` — только показать список.

Спорные файлы (не whitelist, не явный черновик) — **не удаляем**, оставляем как есть, без вопросов. Цель шага — убрать очевидный мусор, не разбираться в каждом файле.

## Шаг 3. Коммит изменений сессии

Базовая классификация по `git status`:

- **моё (touched)** — попадает в коммит автоматически, **без вопросов**.
- **чужое** — файл в status, но не в touched → молча исключаем, в финальной сводке упоминаем одной строкой «оставлено вне коммита: N файлов».
- **смешанный** — файл в touched, но в `git diff` есть маркеры `№%` **вне** `session-markers` (или дифф шире правок сессии по tool calls). В коммит — **только свои чанки**, чужие остаются в рабочем дереве unstaged.
- **неоднозначно** — агент **не может** определить принадлежность к сессии по своей истории tool calls и контексту чата. Только такие файлы — повод для уточнения. Если их нет — вопрос не задаём.

### Смешанные файлы — partial stage (только свои чанки)

Один файл может нести несколько changes ([git-workflow.md](../../../docs/ai/git-workflow.md)). `git add <path>` на такой файл закоммитит и чужие правки — **запрещено**.

**Детект смешанности** (для каждого touched-файла в `conf/` / `cfe.xml/`):

```bash
rtk git diff -- path/to/file | grep -oE '№%[A-Za-zА-Яа-я0-9-]*' | sort -u
```

- Маркеры ⊆ `session-markers` (или маркеров нет, но дифф совпадает с правками сессии по tool calls) → **целиком**: `git add path`.
- Есть маркеры ∉ `session-markers` → **смешанный** → partial stage ниже.
- Untracked, созданный в сессии целиком под один change → **целиком** (смешанности нет).

**Алгоритм partial stage**:

Для каждого смешанного файла использовать утилиту `tools/git-partial-stage.py`. Она сама находит границы блоков `№%` (до конца процедуры/области или следующего маркера) и добавляет только нужные хунки в индекс (используя `git apply --cached`), оставляя рабочее дерево нетронутым.

```bash
bash tools/sandbox/run.sh python tools/git-partial-stage.py "путь/к/файлу" --markers №%<session-id-1> №%<session-id-2>
```

Если нужно принудительно добавить конкретные строки (например, правки без маркеров), можно передать диапазоны строк: `--lines 10-20 45-50`.

Проверка перед коммитом: `rtk git diff --staged -- path` не содержит строк с чужими `№%`.

В сводке шага 3 отдельной строкой: `partial: path (только №%<id>, чужие маркеры остались unstaged)`.

### Порядок действий

1. Классифицировать touched: целиком / смешанный / неоднозначно. Показать **короткий** итог: «к коммиту: N файлов (из них partial: K)», «вне: M файлов». Полный список — под катом / опционально.
2. **Дробление на несколько коммитов — по умолчанию НЕТ.** Один коммит на всё touched. Дробить только если в touched **явно** смешаны несвязанные темы (например, 2+ разных OpenSpec change с разными `<id>`, либо feat по одной подсистеме + несвязанный fix по другой). При срабатывании триггера — один короткий вопрос: «один коммит или N по темам?». В остальных случаях — один коммит без вопроса.
3. Если есть «неоднозначно» — **один** общий вопрос со списком: «включить в коммит / оставить вне / удалить». Если «неоднозначно» нет — переходим сразу к коммиту **без подтверждения состава** (touched-список уже определён скиллом, пользователь не должен его пересматривать).
4. Stage: целиком — `git add path`; смешанные — partial stage выше. **Не** `git add -A`, **не** `git add .`. Затем [`/git-summarize-and-commit`](../../../.cursor/commands/git-summarize-and-commit.md) (при дроблении — отдельный вызов на группу; если index уже собран partial stage — не перезатирать `git add` целыми файлами).
5. Не пушить (push — только по явному запросу, см. [CLAUDE.md](../../../CLAUDE.md)).

На `--dry-run` — только показать классификацию и предполагаемые сообщения, не коммитить.

**Принцип шага 3**: пользователь не должен подтверждать состав коммита, если принадлежность файлов сессии определяется однозначно. Вопрос — это исключение, не норма.

## Что скилл НЕ делает

- Не пушит в remote.
- Не правит `memory/`, `memory.md` и `docs/ai/` автоматически на close-chat
  (агент пишет memory **во время** сессии; шаг 0б — **предложение** оператору
  перенести уроки в docs, см. [agent-session-lessons.md](../../../docs/ai/agent-session-lessons.md)).
- Не трогает untracked-файлы, которых нет ни в whitelist, ни в touched-списке.
- Не архивирует OpenSpec changes, которые не трогали в этой сессии.
- Не запускает `check-bsl.py`, тесты и сборку — это отдельные шаги, юзер решает сам.
- Не каскадит при обрыве: если на любом шаге пользователь сказал «стоп» — остановиться, ничего не откатывать.
- **Не задаёт лишних вопросов.** Каждый вопрос пользователю должен быть оправдан: либо реальный блокер (шаг 0), либо удаление файла из whitelist/handoff (шаг 2, одно общее подтверждение), либо неоднозначная принадлежность файла к сессии (шаг 3, только при наличии таких файлов). Состав коммита из уверенно touched-файлов — без вопросов.

## Границы

- Коммит — только по явному подтверждению пользователя (правило из [CLAUDE.md](../../../CLAUDE.md): «НИКОГДА НЕ ДЕЛАЙ КОММИТЫ БЕЗ ЯВНОГО РАЗРЕШЕНИЯ ПОЛЬЗОВАТЕЛЯ»).
- Удаление файлов — только по whitelist автоматически; всё прочее — через подтверждение.
- Спорные файлы и оформление будущих задач — через [`/handoff`](../handoff/SKILL.md), не через память.
- Если в сессии вообще не было правок — шаги 1–3 пропустить, сказать «коммитить нечего».
