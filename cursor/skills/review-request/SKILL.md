# review-request — заявка на ревью (исполнитель)

Ты **исполнитель**. Описываешь свою работу для ревьювера: что сделал, что
проверить, где затык, в чём сомневаешься. Пишешь **заявку** в тред ревью
`handoffs/<slug>/rN-request.md`. Это рабочий канал между двумя сессиями, не спека
и не долговременная память.

**Принцип:** ссылаться на устойчивые артефакты (`openspec/`, `memory/`, коммиты,
дифф по маркерам `№%`), не копировать их.

**Парный скилл:** вердикт по заявке пишет ревьювер —
[review](../review/SKILL.md). Этот скилл — только сторона исполнителя. Не путать
роли: тут ты НЕ выносишь вердикт, ты ОПИСЫВАЕШЬ работу и просишь проверить.

**Отличие от [handoff](../handoff/SKILL.md):** `handoff` — generic-снимок сессии;
заявка — направленный запрос ревьюверу с фокусом проверки. Термины:
[CONTEXT.md#language](../../../CONTEXT.md#language).

## Когда вызывать

«оформи на ревью», «заявка на ревью», «передай ревьюверу». Часто — когда работа
не закончена, агент уперся в задачу, или есть сомнения в корректности результата.

Если просят **дать вердикт** («сделай ревью», «запиши вердикт») — это другая
роль, переключись на [review](../review/SKILL.md).

## Аргументы

`/review-request <slug>`

- `<slug>` — единица треда ревью. Имя openspec change, если ревью привязано к
  change; иначе свободный kebab-топик (без даты-префикса). Пример:
  `upd-tnved-rashodnaya`, `forms-web-client-blocker`.
- Если `<slug>` не задан — вывести из контекста; при неоднозначности спросить
  одним вопросом.

## Куда писать

Канон — локальный каталог `handoffs/<slug>/` (вне git, в `.gitignore`). Тред =
`<slug>` (аргумент скилла).

Новый тред:

1. Создать каталог `handoffs/<slug>/`.
2. Текст заявки — `handoffs/<slug>/r1-request.md` (шаблон ниже).

Продолжение треда (тот же `slug`, каталог уже есть): новый раунд — новый
`rN-request.md` в том же каталоге.

**Перед записью** Read целевого md. Нет файла — норма.

### Нумерация раунда

Сканировать `handoffs/<slug>/r*-*.md`:

- `N` = (макс. номер среди всех `r*`) + 1. Первый раунд — `r1`.
- Исключение: есть `rN-request.md` без парного `rN-result.md` — тот же `N`
  (правка заявки), спросить подтверждение на перезапись.

## Шаблон заявки (`rN-request.md`)

Писать нормальным русским — ревьювер должен понять контекст с холода.

```markdown
# Заявка на ревью: <slug> — раунд N

**Когда**: YYYY-MM-DD HH:MM (локальное)
**Ветка / коммит**: <ветка>, <короткий SHA> — <subject> (если git)
**Change**: openspec/changes/<slug>/ (если есть; иначе «нет change»)
**Статус работы**: закончено | не закончено | затык

## Фокус ревью

1-3 предложения: что именно проверить, на что смотреть в первую очередь.

## Нерешённая проблема

Обязательна при статусе «затык» / «не закончено». Иначе опустить.

- **Симптом**: что наблюдается (ошибка дословно, поведение).
- **Что пробовал**: подходы и почему не сработали.
- **Гипотезы**: версии причины.
- **Где застрял**: конкретная точка (файл:строка, метод, развилка).

## Сомнения автора

Точки неуверенности в корректности решения/выводов — что перепроверить.
Если уверен — опустить.

## Состав работы

- Файлы по маркеру `№%<slug>` (не дифф; команда: `git diff | grep -o '№%...'`).
- Ссылки на `openspec/changes/<slug>/` (proposal/design/tasks/spec).

## Ответ по прошлому вердикту

Только начиная с раунда 2. По каждому пункту чеклиста `rN-1-result.md`:
сделано / не сделано / спорно + краткий комментарий.

## Проверки

- BSL: check-bsl.py — пройдено / ошибки / не запускалось.
- XML / тесты — статус или N/A.

## Замечания оператора

Опционально. Устойчивые вопросы/фокус человека для ревьювера (канал A или
перед Task `reviewer`). Разовые реплики — лучше в чате с `/review`, не сюда.
Если нет — опустить.

## Открытые вопросы

К ревьюверу или пользователю. Если нет — опустить.

## Ссылки

- openspec/, memory/, коммиты — без копирования содержимого.
```

## Чего не писать

- Полный текст proposal/design/tasks, кода модулей — только ссылки и `файл:строка`.
- Полный дифф — группировка по маркеру `№%`, не построчно.
- Секреты, токены, пароли, содержимое `.env`, строки подключения.
- Длинные дампы MCP/qmd — итог + параметры запроса для повтора.

## После записи

1. Сообщить пользователю относительный путь и объём (строки).
2. Подсказать следующий шаг (**канал B, default**): фразы
   «отправь на ревью» / «запусти reviewer» / «прогони review» — parent запустит
   Task `reviewer` (см. [review-protocol.md](../../../docs/ai/review-protocol.md)).
   **Канал A** (человек хочет обсудить замечания): новый чат + `/review <slug>`;
   устойчивые замечания — секция «Замечания оператора» в заявке.
3. Кандидаты в долговременную память (повторяющиеся грабли, договорённости) —
   перечислить отдельно; в `memory/` не писать без запроса пользователя.

## Запуск субагента (parent, канал B)

Только по узким фразам выше. **Не** автозапускать сразу после записи заявки.

Prompt Task `reviewer` (минимум):

```text
slug: <slug>
заявка: handoffs/<slug>/rN-request.md
выполни скилл /review (см. .cursor/skills/review/SKILL.md)
```

После завершения Task: путь вердикта + резюме (годен / на доработку /
блокер) + next step. Не вклеивать весь вердикт в чат.

## Границы

- `/review-request` не коммитит и не пушит (`handoffs/` вне git).
- Не заменяет OpenSpec: контракт/спека меняется в `openspec/**`, заявка только
  ссылается. Дрифт требований — по
  [openspec-apply-change](../openspec-apply-change/SKILL.md).
- Не дублирует `memory/` и `handoff`.
- Не гонять по ревью-файлам check-bsl.py / xml-wellformed — это не код.
