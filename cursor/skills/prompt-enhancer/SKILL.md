# /prompt-enhancer — формализация постановки

Адаптация
[comol/ai_rules_1c …/prompt-enhancer](https://github.com/comol/ai_rules_1c/blob/main/content/skills/prompt-enhancer/SKILL.md).
Жанр «prompt enhancer» распространён; **канон текста для нас** — скилл comol
(1С-ориентированный шаблон). Более ранний идентичный источник не зафиксирован.

**Суть:** улучшить **форму**, не содержание. Имена объектов/реквизитов/`яя_*`
переносить дословно. Не добавлять тесты, роли, БСП, логирование, откат — если
их не было в исходнике.

**Не замена** [explore](../explore/SKILL.md): если в исходнике дыры (нет цели,
границ, постановщика) — всё равно улучшить форму и в конце явно пометить
«дыры → `/explore`». Не отказывать в работе скилла.

## Когда вызывать

- `/prompt-enhancer`, «улучши промпт», «формализуй постановку»,
  «прокачай постановку», «структурируй ТЗ / заметку», «сделай постановку точнее»

## Режимы

| Режим | Как выбрать | Результат |
| --- | --- | --- |
| Interactive | аргумент пуст | Спросить текст или путь к файлу |
| File | `Read` пути успешен | Файл в `handoffs/prompt-enhanced/` |
| Inline | путь не существует / просто текст | Вывод в чат |

Определение режима **только** через Read пути, не по наличию `.md` в фразе
(«спека про .md» ≠ путь).

### File-режим — куда писать

Всегда (даже если исходник в `research/` / `openspec/`):

```text
handoffs/prompt-enhanced/<basename>-enhanced.md
```

- Папка ленивая (создать при первой записи). `handoffs/` в `.gitignore`.
- Исходник не трогать, не удалять, не переименовывать.
- Повторный запуск — перезаписать `*-enhanced.md` без спроса.
- Не класть рядом с change/docs — чтобы не засорять git.

Не путать с `handoff-*.md` (снимок сессии) и `rN-request.md` (ревью).

## Принципы преобразования

1. **Исходник = единственный источник истины.** Термины, имена, числа — дословно.
2. **Императив.** «нужно показать» → «Показать»; план действий, не рассказ.
3. **Edge cases явно.** «если …, то …» отдельным предложением.
4. **Формат вывода.** Секция «Для каждого элемента укажи» + формат (таблица /
   список / JSON).
5. **Без новых требований.** Не выдумывать то, чего не было в исходнике.
6. **Нумерация шагов.** Дискретные проверяемые операции 1..N.
7. **Сохранить намерение.** Если «список» на деле анализ — сначала анализ.
8. **Нейтральный регистр.** Убрать «было бы неплохо», «как-нибудь».
9. **Суть в первой строке** — цель одной фразой, потом шаги.
10. **Форматирование** — [markdown-formatting.md](../../../docs/ai/markdown-formatting.md)
    (не копировать запрет «ё»/тире из upstream).

## Шаблон результата

1. **Цель** — одно предложение.
2. **Шаги анализа** — нумерованный список императивов.
3. **Граничные случаи** — явные «если …, то …».
4. **Формат вывода** — тип + поля.
5. **Уточнения** (опц.) — только из исходника.
6. **Дыры для explore** (если есть) — список пробелов; «дальше `/explore`».

## Пример (сжатый)

**Исходник:** вкладка «Доп. реквизиты» в конец; если только один служебный
реквизит — ничего не делать; список объектов и разбор форм.

**Результат:** цель → шаги (найти объекты, изучить формы, добавить вкладку,
перенести реквизиты) → исключение «только служебный» → таблица полей на объект →
при отсутствии списка объектов в исходнике: «дыры → explore».

## DO / DON'T

**DO:** дословные имена; императивы; edge cases; явный формат вывода; пометка
дыр для explore.

**DON'T:** новые требования; обобщения вместо имён; «сделай через БСП», если
не сказано; оценки сроков/ROI.
