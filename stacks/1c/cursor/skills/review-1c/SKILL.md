# review-1c — 1C-дополнение к review

Читается из `review` до шага 1, когда у потребителя выбран стек `1c`.
Стеко-специфичные проверки для 1С-потребителя (продолжение списка
«Обязательные проверки» core-скилла):

- **Размещение кода в типовых модулях** (особое внимание): новый код в типовом
  (вендорском) модуле — преимущественно в области `яя_`. Вне `яя_` — только при
  необходимости (когда инъекция технически обязана стоять в типовом методе) и
  **обязательно** с комментариями модификации по стандарту проекта. Код вне `яя_`
  без обёртки комментариями или без обоснования необходимости → блокер.
- **Только программные изменения форм**: правки форм — программно (например
  `ИзменитьРеквизиты`, добавление элементов/команд в коде модуля формы).
  Правки `Form.xml` (разметка, реквизиты формы) → блокер. Grep изменённых
  `**/Forms/**/Ext/Form.xml` в диффе → находка 🔴.
- **Code-as-spec REQUIREMENT-анкеры**: если change затрагивает `яя_`-код в
  `conf/` — каждый новый/изменённый значимый экспортный метод SHALL нести
  REQUIREMENT-блок над сигнатурой (после док-коммента). Проверить:
  - `spec-lint check` зелёный по изменённым файлам (запустить через sandbox)
  - каждый REQUIREMENT привязан к живому методу (нет оторванных анкеров от
    удалённых методов)
  - нет дублей REQ-ID в диффе (два метода с одним ID → 🔴)
  - дрифт требований из `implementation-notes.md` отзеркален в анкеры
  - если capability уже code-as-spec (`<!-- render -->`) — нет prose-only
    Requirement в spec.md без соответствия анкеру (разрешены только Purpose и
    ручные секции)
  Отсутствие REQUIREMENT на значимом методе → 🟠. Дуэли REQ-ID → 🔴.
- При глубоком ревью — стековые скиллы `.cursor/skills/bsl-check`,
  `.cursor/skills/code-analysis-orchestrator`.
