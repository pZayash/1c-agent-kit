# /db-server — отладочный узел 1С на автономном сервере

Поднимает **автономный сервер** (`ibsrv.exe`, «1С:Предприятие 8. Автономный
сервер») на **копии** файловой базы: веб-клиент + HTTP-сервисы (MCP) +
прямое соединение для конфигуратора + сервер отладки.

## Когда применять

- **dev-ИБ потребителя может жить на автономном сервере** (вместо публикации
  Apache): канон и процедуры — док потребителя (пример: `docs/ai/dev-ib-ibsrv.md`).
- Нужна **отладка** конфигурации (точки останова, стек, серверный код) —
  у автономного сервера для этого есть `--debug`.
- Нужен второй контур рядом с публикацией Apache: копия базы под сервером,
  основная база остаётся на Apache.

Файловая база **эксклюзивна**: если базу отдаёт ibsrv, публикация Apache по той же
базе работать не будет (и наоборот — первый старт на занятой базе падает с
«Ошибка исключительной блокировки информационной базы», см. Грабли).

## Что нужно в `.env`

| Ключ | Смысл |
| --- | --- |
| `IBSRV_PATH` | путь к `ibsrv.exe` |
| `IBSRV_DB_PATH` | каталог **копии** файловой базы |
| `IBSRV_NAME` | имя базы на сервере (для `/S`) |
| `IBSRV_DATA` | каталог данных сервера (вне репозитория) |
| `IBSRV_HTTP_*` | адрес/порт/базовый путь публикации |
| `IBSRV_DIRECT_REGPORT` | порт прямого соединения (`/S host:port\name`) |
| `IBSRV_DEBUG`, `IBSRV_DEBUG_PORT` | `http`/`tcp`/`server` и порт отладки |
| `IBSRV_SERVICES` | сервисы расширений через запятую, дефолт `mcp,mcp-dev` |
| `IBSRV_USER`, `IBSRV_PASSWORD` | учётка ИБ для Basic (фолбэк — `WEB_TEST_*`) |
| `IBSRV_PID_FILE` | PID-файл узла; задан → `load-changed-files.sh` работает через `ibcmd --pid` |
| `IBCMD_DATA` | каталог данных `ibcmd` (дефолт `<воркспейс>/.tmp/ibcmd-data`); общий каталог учётки — межпроектный мьютекс `«Ошибка блокировки каталога данных сервера»` |
| `IBSRV_EXTRA_ARGS` | доп. флаги ibsrv (напр. `--enable-extended-designer-features`) |
| `IBSRV_HOLD_TTL` | (опц.) ttl hold оффлайн-цикла в секундах, который ставит движок загрузки (дефолт 45 мин) |

Порты выбирай так, чтобы не пересекаться с Apache-публикацией и другими узлами.

## Команды

Скрипт запускается **на хосте** (не в sandbox): он стартует процесс и читает
хостовые пути.

```bash
SK=".cursor/skills/db-server/scripts/db-server.py"
python "$SK" -Action yaml     # перегенерировать конфигурационный yaml
python "$SK" -Action status   # pid + порты + ВЛАДЕЛЕЦ порта (наш/чужой) + hold + лок старта
python "$SK" -Action start    # запустить и ДОЖДАТЬСЯ готовности (pid+порт+HTTP), rc=0/3
python "$SK" -Action stop     # остановить и поставить .hold с владельцем (пауза)
python "$SK" -Action stop --offline   # hold kind=offline, ttl 45 мин (оффлайн-цикл)
python "$SK" -Action stop --no-hold   # остановить без .hold (только для скриптов)
python "$SK" -Action hold-release     # снять свой hold (конец оффлайн-цикла)
python "$SK" -Action start --force    # снять ЧУЖОЙ hold осознанно (печатает, чей он)
python "$SK" -Action basic --show   # Basic-заголовок для MCP-клиента
```

### Коды возврата (читать rc, а не текст)

| rc | что значит | что делать |
|----|-----------|-------------|
| 0 | узел работает: наш pid владеет портом, HTTP отвечает (`stop`/`hold-release` — снимать нечего) | — |
| 2 | `stop`: не удалось погасить процесс (права/сессия) | pid-файл сохранён, создан `.stop` → `schtasks /Run /TN '\ibsrv\ibsrv-nodes-start'` |
| 3 | `start` не поднял узел: порт не открылся или его держит чужой pid | **не** убивать `taskkill /F`; смотреть лог/владельца порта; подождать 1–2 мин |
| 4 | чужой `.hold` (start/hold-release) **или** ошибка конфигурации: нет `IBSRV_PATH`/`IBSRV_PATH` не файл/нет `IBSRV_DB_PATH` | ждать владельца; `--force` только осознанно; конфиг — поправить `.env` |
| 5 | отказ без действий: лок старта занят (параллельный `start`/`stop`), либо порт держит **чужой процесс** — его `stop` не глушит | подождать 1–2 мин, повторить `status`; чужой порт освобождать у его владельца или сменить `IBSRV_HTTP_PORT` |

`start` больше **не** рапортует успех при закрытом порте (было 2026-11-11: «узел
запущен: pid=…» при всех закрытых портах — агент считал базу поднятой).

**`-Action stop` может не суметь погасить узел** (rc=2): процесс запущен более
привилегированной сессией (bb-агент elevated / задача `\ibsrv\ibsrv-nodes-start`
с RunLevel Highest), а `taskkill` из обычного Git Bash получает «Отказано в доступе».
Скрипт в этом случае честно говорит «НЕ УДАЛОСЬ остановить», **оставляет pid-файл** и
создаёт запрос `<.tmp/ibsrv/.stop>`. Погасить без прав администратора:

```bash
MSYS_NO_PATHCONV=1 schtasks /Run /TN '\ibsrv\ibsrv-nodes-start'   # задача сделает stop по .stop
```

Не «лечить» это удалением pid-файла: узел продолжит держать файловую ИБ, а следующая
загрузка упадёт «Ошибка блокировки информационной базы для конфигурирования».

### Пауза watchdog'а (`.hold`) и её владелец

Если узел держит хост-vigil (задача `\ibsrv\ibsrv-nodes-start`, поднимает узел
каждые 10 мин), то на время оффлайн-цикла `ibcmd` (импорт + `apply`, 20–25 мин
на метаданных) её надо притормозить: `-Action stop` ставит `.tmp/ibsrv/.hold`.
Watchdog его видит и базу не трогает. Права администратора для этого не нужны.

С 2026-11-11 `.hold` — **JSON с владельцем**, а не пустой файл:

```json
{"kind": "pause|offline", "ttl": 2700, "since": 1794400035,
 "owner_user": "p.zayash", "owner_thread": "thr_xxx", "owner_cwd": "...", "reason": "..."}
```

Правила:

- `-Action start` снимает hold **только** если это hold того же треда (`BB_THREAD_ID`),
  он протух (возраст > `ttl`), он пустой/легаси, либо явно `--force`.
  Чужой живой hold → `rc=4` с owner/reason — так чужой оффлайн-цикл больше не рвётся
  (09.11: `-Action start` из треда выписок снимал hold чужого `apply`).
- Свой цикл вручную: `-Action stop --offline` → работа → `-Action start` (снимет сам).
- `-Action hold-release` — снять **свой** hold, не поднимая узел (чужой — только
  с `--force`, иначе `rc=4`). Это же делает движок `load-changed-files.sh`:
  `stop --offline` перед оффлайн-циклом и `hold-release` в конце прогона.
  Без этого документированный возврат узла `-Action start` **из другого треда/шела**
  упирался в собственный hold (`rc=4`) и узел лежал до истечения ttl (2026-11-12).
- **Забытый hold** = база не поднимется автоматически. `-Action status` печатает
  owner/reason/возраст/ttl; после истечения ttl `start` снимет его сам.
- Watchdog ставит/снимает hold сам и передаёт `--no-hold` при остановке (в старом
  ките флага не было — теперь это проверяется, см. `start-ibsrv-nodes.ps1`).

### Лок старта и владелец порта

- `.tmp/ibsrv/.start.lock` — мьютекс `start` **и `stop`**: два одновременных
  `start` (агент + watchdog + руками) невозможны, второй получает `rc=5`;
  `stop` берёт тот же лок, иначе окно «start увидел pid → stop убил» давало агенту
  `rc=0` при мёртвом узле. Протухший лок (pid мёртв или старше 5 мин) снимается сам.
- **Владелец порта — истина, pid-файл — подсказка.** `status`/`start`/`stop` берут
  владельца `IBSRV_HTTP_PORT` через `netstat -ano` (`lsof` на Linux); чужой процесс не
  убивается, а называется в тексте (`rc=3` в `start`). `stop` гасит владельца порта,
  даже если pid-файл протух, — **но только если это наш узел**: сначала проверяется
  образ процесса (`ibsrv`) и, если командная строка читается, база из `--config`
  (сверка с `IBSRV_DB_PATH`). Порт держит не ibsrv или ibsrv **другой базы** →
  `rc=5`, процесс жив, в тексте pid/образ/командная строка.
- `ibsrv.log` больше не перезаписывается: предыдущий прогон остаётся в `ibsrv.log.prev`.

Проверка MCP после старта:

```bash
curl -s -X POST "http://localhost:<IBSRV_HTTP_PORT>/hs/mcp/rpc" \
  -H "Authorization: Basic <base64 UTF-8>" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

## Конфигурационный yaml (публикация сервисов)

HTTP-сервисы **расширений** на автономном сервере не публикуются сами —
их надо перечислить в конфигурационном файле (`--config`), иначе сервис
отдаёт `503` с внутренней ошибкой `sessionId != kUUIDNull`. Канон структуры —
`ibcmd server config init`; ключ `http-services` **вложен** в элемент `http`:

```yaml
server:
  address: 'localhost'
  port: 8315
database:
  path: 'C:\Bases\copy'
infobase:
  id: '<uuid>'
  name: 'copy'
  distribute-licenses: yes
  schedule-jobs: allow
http:
  base: '/'
  http-services:
    publish-extensions-by-default: yes
    service:
    - name: 'mcp'
      root: 'mcp'
      publish: true
```

Разбор параметров: раздел «Standalone server configuration file» гайда
Administrator Guide (kb.1ci.com, Appendix 3) — см. память проекта.

## Отладка

1. `python db-server.py -Action start` (в `.env` задан `IBSRV_DEBUG=http`).
2. Конфигуратор: подключиться к `/S"<IBSRV_HTTP_ADDRESS>:<IBSRV_DIRECT_REGPORT>\<IBSRV_NAME>"`.
3. В конфигураторе — отладка по адресу сервера отладки (порт
   `IBSRV_DEBUG_PORT`), либо запуск клиента к тому же `/S`.

## Грабли

- **Файловая база эксклюзивна.** Пока ibsrv держит базу, публикация Apache по
  той же базе падает («Ошибка разделенного доступа»). Первый перевод базы на ibsrv:
  `Stop-Service Apache2.4` → старт узла → `Start-Service Apache2.4`
  (ИБ держит worker httpd.exe через wsap24.dll).
- **Аутентификация MCP — Basic**, не JWT: `accessTokenAuthentication` из
  `default.vrd` конфиг автономного сервера не описывает.
- **`/UpdateDBCfg` конфигуратором через `/S` рвёт сеанс**
  (`recv returns zero`, ассерт `m_dbOperationsBlock` в `workerHostImpl.cpp`) —
  загрузку `conf/` делать движком `ibcmd` (удалённый `--pid`).
- **MSYS переписывает POSIX-пути в env-переменных**: `IBSRV_HTTP_BASE="/"` без
  `MSYS_NO_PATHCONV=1` при запуске из Git Bash уезжает в `C:/Program Files/Git/`.
- **Basic-учётка — только UTF-8.** `curl -u` в Git Bash/MSYS отправляет
  кириллицу в cp1251/cp866 → платформа отвечает `401`. Собирай заголовок
  скриптом (`-Action basic --show`) или явным `Authorization: Basic …`.
- **Запуск из агентского шелла.** Процесс, оставшийся в консоли/дереве
  вызова, вешает Bash-инструмент — поэтому запуск detached
  (`DETACHED_PROCESS`/`start_new_session`).
- **`--http-base=/` из Git Bash** уезжает как `C:/Program Files/Git/`
  (нужен `MSYS_NO_PATHCONV=1`).
- Сервер отдаёт `401` без кредов и `503` для непубликованного сервиса —
  это разные диагнозы: 503 = нужен `http-services` в yaml.
- **`-Action stop` без `--no-hold` ставит `.hold`.** Это намеренно (агент гасит узел
  под оффлайн-цикл), но если узел гасит автоматика — только `--no-hold`, иначе
  неудачный старт оставит hold и watchdog перестанет поднимать базу. Движок
  загрузки ставит `--offline` (ttl 45 мин, переопределяется `IBSRV_HOLD_TTL`) и
  снимает hold сам в конце прогона — если конфигуратор/клиент движок не запускал;
  база за запущенным конфигуратором → hold остаётся (`-Action hold-release` после).
- **`-Action status` не доказывает живость.** Строка `запущен pid=<pid>` печатается,
  даже когда порты закрыть; смотреть строки `слушает/закрыт` и `curl` → `200`.
