# Соглашения по объектам конфигурации

Правила префикса, подсистем, UI-маркера и имён общих модулей — в доке потребителя,
если есть. Здесь — общее для доработки типовой 1С.

## Добавленные объекты

- Новые объекты — с **префиксом потребителя** (не дублировать префикс в именах
  методов/реквизитов **внутри** уже префикснутого объекта).
- Префикс в имени метода/реквизита — для дополнений **типовых** объектов и модулей
  (область правок в конце типового модуля).
- Область правок потребителя — **только в типовых** объектах. В своих объектах
  весь модуль и так свой; методы — в обычные области по смыслу.
- **Исключение по имени.** В своём объекте префикс в имени метода оправдан, только
  если он **повторяет одноимённый метод типовых собратьев** (паритет интерфейса).
- **Однотипная доработка на семействе документов — единый паттерн на всех.**
  Разнобой допустим только с явной причиной в комментарии.
- Добавленные объекты — в подсистему потребителя (или её подчиненные).
- Длина индексов добавленных объектов не должна превышать 1920 байт
  (максимальная длина индексируемого текстового поля — 625 символов).
- Версионирование: `yyMMdd.XX`.

## Псевдонимы UI

Если у потребителя есть видимый маркер доработок в синонимах/заголовках —
только в тексте для пользователя, не в `Name` и не в именах процедур.
Типовые объекты не переименовывать ради маркера без явного UI-переопределения.

## Логика типового документа: модуль объекта и менеджер

Доменная логика **одного** типового документа — **не** в общем «свалковом»
модуле и **без** префикса `ИмяДокумента_` в имени метода.

| Контекст | Модуль | Вызов |
| --- | --- | --- |
| Работа с данными документа (`ЭтотОбъект`) | **модуль объекта**, область правок | метод без параметра «объект»; из формы: `РеквизитФормыВЗначение` / обратно |
| Работа по **ссылке**, запросы, close-warning по сохранённому | **модуль менеджера**, область правок | `Документы.ИмяДокумента.Метод(Ссылка)` |

В общем модуле остаются только **кросс-документные** фасады, делегирующие
в менеджер конкретного документа.

## Ссылочные геттеры (константы конфигурации)

**Ссылочный метод** — экспортный геттер, возвращающий ссылку на **конкретный**
элемент справочника. Два подвида: нав-ссылка (`e1cib/data/...?ref=`) vs поиск
по реквизиту (`НайтиПоКоду` / `НайтиПоНаименованию`).

### UUID хранить нав-ссылкой, не GUID

Для элемента с фиксированным UUID — **навигационная ссылка**, не
`Новый УникальныйИдентификатор("…")`. Аналитик копирует строку в
`Сервис → Перейти по ссылке`. Префикс перед `e1cib/...` — подпись, на разбор
не влияет.

> **Ловушка byte-swap.** Hex после `ref=` — **не** `УникальныйИдентификатор`.
> Половины UUID переставлены. Никогда не подставляй hex из `ref=` в
> `Новый УникальныйИдентификатор`. Ссылку — через хелпер нав-ссылки потребителя;
> UUID — `ссылка.УникальныйИдентификатор()`.

> **Ловушка dev ≠ prod.** Один предметный элемент в разных ИБ может иметь
> **разный UUID**. Нав-ссылка из dev на prod может дать битую ссылку.
> Перед merge проверяй элемент в prod. Предпочитай поиск по стабильному
> реквизиту, если UUID не гарантирован одинаковым.

### Самосоздание для критичных-на-старте элементов

Если элемент **обязан существовать во всех ИБ** и его отсутствие роняет код —
геттер **самосоздающийся**: при отсутствии создать с тем же UUID и
**основными** реквизитами (идентификация, не функциональное наполнение).
Зависимости-ссылки — собственные самосоздающиеся геттеры, раньше владельца.
Не ставить самосоздание на горячий путь и в RLS (read-only).

Смоук: каждый такой геттер возвращает **существующую** ссылку
(`ЭтоЗаполненнаяСсылка` недостаточно — битый GUID тоже «заполнен»).

## Права доступа

- Новым объектам — права в роли базовых прав потребителя, кроме интерактивного удаления.
- Интерактивное удаление у добавленных объектов — выключено для всех ролей.
- Новые **общие формы** — сразу **Просмотр (View)** в роли базовых прав
  (иначе `ОткрытьФорму` → «Недостаточно прав для просмотра»).

## Изменение объектов поставщика

- В дереве поддержки снимать объекты точечно.
- Массово менять правила поддержки запрещено.

### Инъекции в типовые модули

В месте вставки типового — **запрещена** логика. Вся логика — в модуле швов
потребителя (имя метода = `ИмяМодуля_ИмяМетода`, комментарий `// см.`,
заглушка `Если Ложь Тогда` для поиска ссылок).

В типовом — одна строка вызова + маркер правок потребителя.

### Запрещенные изменения типовых объектов

- Добавлять предопределенные элементы (менять — только по существенной причине)
- Типовые макеты печатных форм
- Элементы и реквизиты типовых форм в редакторе (только программно)
- Типовые роли (для изменения — расширение)
- Типовые подсистемы

## Квалификаторы типов в XML

При ручном XML используй **только** теги XDTO платформы.
Имена из конфигуратора и SQL **не совпадают** с XML:

| Конфигуратор / SQL | XML-тег XDTO |
|--------------------|--------------|
| Длина / Precision | `v8:Digits` |
| ТочностьДробной / Scale | `v8:FractionDigits` |
| ДопустимыйЗнак | `v8:AllowedSign` (`Any` / `Nonnegative`) |
| Длина строки | `v8:Length` |
| ДопустимаяДлина | `v8:AllowedLength` (`Variable` / `Fixed`) |
| ЧастиДаты | `v8:DateFractions` (`Date` / `Time` / `DateTime`) |

Пример числового ресурса (Число 15,0):

```xml
<Type>
    <v8:Type>xs:decimal</v8:Type>
    <v8:NumberQualifiers>
        <v8:Digits>15</v8:Digits>
        <v8:FractionDigits>0</v8:FractionDigits>
        <v8:AllowedSign>Any</v8:AllowedSign>
    </v8:NumberQualifiers>
</Type>
```

> **Ловушка**: `Precision`/`Scale`/`NonNegative` — ошибка XDTO при загрузке.
> Полная справка: [1c-config-objects-spec.md](specs/1c-config-objects-spec.md).

**Ловушка DSL `Number(3)`**: в `meta-edit` / `meta-compile` один аргумент не
парсится → в XML `<v8:Type>Number(3)</v8:Type>`. В DSL всегда `Number(3,0)`.
Прочие артефакты: [metadata-xml-load-pitfalls.md](metadata-xml-load-pitfalls.md).

## Формы

- Только управляемые формы.
- Изменения в типовых формах — программно, не в редакторе.
