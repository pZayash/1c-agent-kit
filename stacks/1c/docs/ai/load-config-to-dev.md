# Загрузка конфигурации в dev-ИБ (для агентов)

Процесс и роль того, кто грузит (интегратор: цикл, доказательства применения, грабли) —
[agent-integrator.md](agent-integrator.md). Ниже — механика самого движка загрузки.

## Канон

Залить изменения из git (`conf/`, `cfe.xml/`) в **dev-базу** — только:

```bash
./load-changed-files.sh
```

С обновлением структуры БД после правок метаданных:

```bash
./load-changed-files.sh -U
```

Навык: **`/load-changed-files`**.

Ядро скрипта — `harness/tools/load-changed-files/` (kit). Корневой
`load-changed-files.sh` потребителя — thin wrapper.

Настройки: `.env` (`IB_CONNECTION`, `DESIGNER_PATH`, `CONFIG_PATH`,
`EXTENSIONS_PATH`). Шаблон ключей: [templates/env.example](../../../../templates/env.example).

Остановка публикации нужна только для **файловой** ИБ (`IB_CONNECTION=/F…`): её
держит worker Apache (`wsap24.dll`). Для серверной (`/S…`) и для автономного
сервера (`ibsrv` + `IBSRV_PID_FILE`) скрипт Apache не трогает.

Зависимости потребителя (не в kit): `tools/load-project-env.sh`, `tools/os/`.

## Не использовать

Upstream cc-1c: `db-load-git`, `db-load-xml`, `db-update`, `db-load-cf` —
исключены из sync. Канон — `./load-changed-files.sh`.

## Типовые флаги

- **`-U`** — `/UpdateDBCfg` после загрузки (почти всегда после метаданных).
- **`--no-extensions`** — только `conf/`, без `cfe.xml/`. **Обязателен**, если
  агент не менял расширения (защита от чужих правок в worktree). Маркер HEAD
  пишется как обычно; **исключение**: в диапазоне маркера есть дельта
  `cfe.xml/` — тогда маркер НЕ обновляется (иначе committed-дельта расширений
  потерялась бы) + WARN с рецептом догрузки.
- **`--list-file PATH`** — фолбэк: явный список вместо git-discovery.
- **`-F` / `--full-resync`** — вся `conf/` без partial; когда ИБ отстала от
  диска после merge («Неизвестный объект», exit 21).
- **`--reset-marker`** — удалить файл маркера (мёртвый SHA). **Не** канон
  «залить merge»: на чистом дереве это был бы только UpdateDB; скрипт на
  merge-HEAD сам берёт `HEAD^1`.
- **`--force-partial`** — форсировать `--partial` даже при `Configuration.xml`
  в списке. Без флага список с корневым файлом идёт **changeset-режимом**
  (`files`/`-listFile` без `--partial`): единственный путь, где грузится
  `Configuration.xml` (в `--partial` ibcmd его отвергает). Changeset проверяет
  всю конфигурацию (минуты) и применяет удаления объектов из `ChildObjects`.
- **`--ibcmd`** / `LOAD_ENGINE=ibcmd` — headless/CI (медленнее designer).
  **Автономный сервер (`IBSRV_PID_FILE` задан):** тот же движок идёт через шлюз
  администрирования `ibcmd --pid=<pid>`: монопольного доступа нет, Apache и сервер
  не останавливаются; список файлов — относительные пути к `--base-dir`.
  Конфигуратор по `/S` на `/UpdateDBCfg` на автономном сервере рвёт сеанс
  (`recv returns zero`, ассерт `m_dbOperationsBlock`) — использовать `ibcmd`.
  **Каталог данных `ibcmd` (`IBCMD_DATA`)** — свой на воркспейс, дефолт
  `<воркспейс>/.tmp/ibcmd-data`. Платформенный дефолт (`%LOCALAPPDATA%\1C\1cv8\
  standalone-server`) один на учётку Windows и защищён `lock.pid`: два параллельных
  `ibcmd` из разных проектов не работают одновременно — второй падает
  «Ошибка блокировки каталога данных сервера» (код 127). `IBCMD_DATA=shared` —
  осознанно вернуть общий каталог (сериализация всего хоста).
  Подробности — док потребителя (`docs/ai/dev-ib-ibsrv.md`).
- **`--drop-designer-sessions`** / `IB_LOAD_DROP_DESIGNER_SESSIONS` — явно разрешить
  снятие висячих сеансов «Конфигуратор» в ИБ через `ibcmd session terminate`
  (защита 4 ниже). Узел скрипт не перезапускает никогда.
- **Автозакрытие процессов — только явное.** `-H`, `-C`, `--refresh-variants`
  управляют только своим поведением (verbose + переоткрыть конфигуратор/клиент)
  и **не включают** `AUTO_CLOSE_DESIGNER`/`AUTO_CLOSE_CLIENT`: убитый
  `taskkill`'ом процесс может оставить в ИБ висячий сеанс «Конфигуратор»
  (ibsrv), который блокирует следующие загрузки. Закрытие — только
  `-n`/`--allow-close-designer` и `AUTO_CLOSE_CLIENT=true` в `.env`.
  После убийства процессов `close_1c_designer` проверяет, что сеанс в ИБ
  реально освободился (проба `ibcmd session list --pid`, tools/os потребителя);
  не освободился — отказ с командой рестарта узла, молча узел не перезапускается.
- **`--force-sessions`** / **`--no-force-sessions`** — разрешить/запретить авто-retry
  `/UpdateDBCfg` при ошибке «обнаружены клиенты, работающие по HTTP». Env:
  `UPDATE_DB_FORCE_SESSIONS` (по умолчанию `true`).

После merge: `./load-changed-files.sh -U`. Стоп: `Загрузка пропущена; только
UpdateDB` при ненулевой дельте `conf/` — смотри exit 21, затем `-F -U`.
`LOAD_HIDE_FILES` в `.env` прячет битые типовые формы на время designer.

Подробности — skill `/load-changed-files` и docs потребителя.

## Защиты движка (ворктри / чужая грязь / параллельные загрузки)

Движок сам предупреждает об опасных запусках (одна dev-ИБ на всех, загрузки
централизованы). Четыре проверки выполняются одним блоком перед началом
загрузки — **после** `--help` и раннего выхода «нет файлов к загрузке».

Env-гейты (в `.env` потребителя):

- **`IB_LOAD_STRICT`** (по умолчанию `false`) — `true` делает проверки 1 и 2
  жёстким отказом (exit) вместо предупреждения;
- **`IB_LOAD_FROM_WORKTREE`** (по умолчанию `false`) — осознанное разрешение
  грузить из ворктри (гасит только проверку 1). Флаги принимают `true`/`1`.

1. **Запуск не из главного чекаута.** Главный ворктри — первая запись
   `git worktree list --porcelain`; текущий — `git rev-parse --show-toplevel`.
   Не совпало и нет `IB_LOAD_FROM_WORKTREE` → `WARN` (при `IB_LOAD_STRICT` —
   `ERROR` + `exit 21`): загрузка из ворктри подменит конфигурацию ИБ дампом
   этого ворктри. Нет git / отвязанный HEAD — тихо пропускается.
2. **Чужая незакоммиченная грязь `conf/` в других ворктри.** Обходит
   `git worktree list --porcelain` (кроме текущего) и смотрит
   `git -C <путь> status --porcelain -- conf/`; непусто → `WARN` с перечнем до
   10 путей. При `-F` (полная пересборка) с `IB_LOAD_STRICT` — `ERROR` + `exit 22`;
   частичная загрузка — только `WARN`. Ошибки `git` при обходе — best-effort.
3. **Похоже, загрузка уже идёт по НАШЕЙ ИБ.** Сужает по basename базы из
   `IB_CONNECTION` (Windows: `1cv8.exe` с `CONFIG` или `ibcmd.exe`; Linux:
   `pgrep -af "1cv8|ibcmd"`). Читающие подкоманды `ibcmd` (`list`/`export`/
   `dump`/`help`) исключаются — они не пишут. Путь ИБ не распознан — тихо
   пропускается. Найдено → `WARN` с PID; жёсткого отказа нет даже при
   `IB_LOAD_STRICT` (риск ложных срабатываний — открытый конфигуратор/клиент).

Раньше защит срабатывает WSL-preflight: WSL-баш + виндовые пути
(`C:/`, `C:\`) в аргументах или `.env` → `ERROR` + `exit 25` («зовите
`/usr/bin/bash`» — MSYS; WSL и MSYS различаются путями и localhost).
WSL + `localhost`/`127.0.0.1` без виндовых путей → только `WARN`.

### Безопасная проверка защиты 3

Защита 3 ловит «параллельную загрузку» по имени процесса (`ibcmd.exe` /
`1cv8.exe CONFIG`), суженному по basename базы из `IB_CONNECTION`. Локальная
проверка легко залипает: фоновый «декой» (поддельный процесс-загрузчик) держит
пайпы инструмента, вызов висит (реальные случаи — 38 и 50 минут, сняты вручную).
Правила:

1. **Боевая база — под запретом.** В `-i`, в декое и в `--db-path` — только
   выдуманный путь (`C:\base\guard-fake-ib`). Настоящий
   `C:\!Pavl0\Работа\КПСР.new\кпср_unf2020.dev.dt` не должен встретиться ни разу:
   при промахе защиты движок реально зальёт дамп из ворктри в общую dev-ИБ.
2. **Всё — в «глухом коконе»**: тест в отдельном `.sh`, снаружи только `timeout`,
   файл лога и `tail`, чтобы пайпы инструмента не были задействованы:

   ```bash
   timeout 180 bash /tmp/guard-test.sh > /tmp/guard-test.out 2>&1 </dev/null
   echo "rc=$?"; tail -30 /tmp/guard-test.out
   ```

3. **Декой сам завершается и не читает stdin** (процесс с именем `ibcmd.exe`, в
   командной строке которого есть выдуманный путь). Если декой залипает — **бросай
   тест**, в отчёте честно: «вариант X не проверен / проверен иначе».
4. **После теста** — проверка «не осталось ли процессов» (`Get-CimInstance` по
   имени/пути) и явный kill.

5. **Висячий сеанс «Конфигуратор» в ИБ** (`-F`, движок `ibcmd`, либо задан
   `IBSRV_PID_FILE`). Прерванный прогон оставляет в ИБ сеанс конфигуратора без
   живого процесса — дальше любые конфигураторные операции отвечают «уже
   работает конфигуратор…». Проба — `ibcmd session list --pid=<узел>` через
   функции `tools/os/process-1c.sh` потребителя; креды проба берёт по цепочке
   `AGENT_IB_*` → `IB_*` → `IBSRV_*` → `WEB_TEST_*` (в `.env` потребителя пароль
   автономного сервера лежит в `IBSRV_PASSWORD`, логин — в `IBSRV_USER`)
   Проба **обязана различать «сеансов нет» и «проба недоступна»**: `ibcmd`
   печатает баннер «требуется аутентификация…» и на чистой ИБ тоже, поэтому
   признак недоступности — ненулевой код возврата или явный отказ идентификации,
   а не текст баннера. Иначе защита молча уходит в «пропускаю» именно на чистой
   базе, а журнал пишет `probe-unavailable` вместо `none`.
   Найден сеанс → жёсткий отказ (exit 23) с подсказкой (`session terminate`
   или рестарт узла). Автоочистка — только явным `--drop-designer-sessions`.
   Проба не снялась → загрузка идёт **без проверки** висячего сеанса: в лог —
   WARN, в журнал — `designer_sessions=probe-unavailable`.

Проверяемые кейсы: чужой процесс (`rt.dev.dt`) — предупреждения нет; наш
`ibcmd`/`1cv8 CONFIG` — есть; `ibcmd extension list`/`config export` — нет.

## Журнал загрузок

Каждая попытка загрузки дописывает одну JSON-строку в
`.tmp/load-history.jsonl` (append-only, не в git): argv и флаги, движок, время
старта/конца и длительность, exit-код, результат (`ok|skipped|refused|aborted|
error`), причина остановки, что грузилось (файлы/расширения/ветка/HEAD),
состояние сеанса конфигуратора и поколение конфигурации до/после («после» —
из строки «Создано поколение конфигурации» в логе 1С, «до» — из предыдущей
записи журнала). По нему видно «что было раньше» без раскопок логов:
`tail -5 .tmp/load-history.jsonl`.

## Preflight поддержки объектов

При partial-загрузке `conf/` скрипт делает preflight объектов на поддержке
(`Ext/ParentConfigurations.bin`). `parent_config.py` резолвится по порядку:
`PARENT_CONFIG_PY` → `scripts/parent_config.py` потребителя → канон
`harness/tools/load-changed-files/parent_config.py` (kit). Если файла нет
нигде — preflight пропускается с `WARN`, загрузка продолжается. Альтернатива —
`-F` (full-resync без preflight).

Внутренний список `-listFile` пишется в `.tmp/changed_files.txt` и удаляется
при любом выходе (успех/ошибка), в корне репозитория артефакт не остаётся.
Рабочие `temp_*.txt` движка тоже снимаются на любом выходе (EXIT-trap), так что
`git status` потребителя остаётся чистым даже при падении `-U`.

## Preflight линтера метаданных (`XML_LINT`)

Перед импортом движок запускает линтер XML потребителя —
`tools/metadata-xml-lint/check.py` (ключ `METADATA_LINT_PY` для своего пути):

- цели: XML дельты `conf/` **и** каталоги изменённых расширений
  (`$EXTENSIONS_PATH/<Имя>`; при `-F` — весь `conf/` + все расширения, если
  `has_extension_changes`). Список передаётся **файлом** (`--list-file`,
  относительные пути от корня репо, `.tmp/xml_lint_files.txt`), а не argv:
  на большой дельте argv упирается в `E2BIG` (400 путей × ~75 симв. →
  «Argument list too long», `rc=126`) и защита молча исчезала ровно на
  больших merge/changeset;
- `LOAD_HIDE_FILES` вычитается: спрятанные файлы прячутся **до** линта (в
  partial — просто не попадают в список, в `-F` — переименованы в
  `*.hidden-for-load`, и обход каталога их не видит). Иначе документированный
  обход «спрятать битую типовую форму» перестанет работать, а сообщение будет
  врать про формат XML;
- линтера нет, либо `python` не найден → `WARN` и загрузка продолжается
  (kit не требует линтер);
- обход: `--no-xml-lint` или `XML_LINT=false` (только осознанно).

### Контракт кодов возврата: стоп только по `1`

| код | смысл | поведение движка |
| --- | --- | --- |
| `0` | находок нет (возможны `[WARN]`) | продолжаем |
| `1` | есть находки `[ERROR]` (в т. ч. «файл не читается») | **стоп до импорта**, `exit 26`, построчно `lint: …` |
| `2` | ошибка использования (плохие аргументы, нет входов) | `WARN` «preflight НЕ выполнен (код 2): <первая причина>», грузим |
| `3` | линтер не смог проверить (среда/внутренняя ошибка) | `WARN` «preflight НЕ выполнен (код 3): …», грузим |
| `4` | локальный код: нет интерпретатора Python (`python`/`python3`/`py -3`) | `WARN` «preflight НЕ выполнен (код 4): …», грузим |

Различение «находки» vs «линтер сломался» принципиально: в bb-worktree
(длина корня ~126 симв.) линтер когда-то отдавал `rc=1` с голым traceback и
ложно блокировал загрузку. Отказывать потребителю можно только по коду `1`.

Цена preflight на `-F`: линтуется **весь** `conf/` — замер 12.11.2026:
4 м 04 с на 47277 XML (в bb-worktree ~3 мин). Движок на `-F` печатает
строку-предупреждение об этом, чтобы это не выглядело зависанием.

⚠ В блоке preflight намеренно **нет** `set -e` (и не надо добавлять):
`lint_rc=$?` после `lint_out=$(…)` с ненулевым кодом линтера убил бы скрипт
до разбора кода возврата, и «стоп только по 1» стало бы «стоп по любому
коду».

Зачем: объект «не в формате дампа» (inline-шаблон в `<ChildObjects>`, нет
`Templates/<Имя>.xml`, `TemplateType` не по содержимому) роняет парсер нативно —
`rc=1` с пустым stderr, mdmp, «молчаливый вис». Стоп за секунды вместо 25 минут
импорта (05.11.2026, `Report.яя_ОстаткиДС`; правила —
`tools/metadata-xml-lint/README.md` потребителя, § «Контракт кодов выхода»).

## UpdateDB: конфликт сеансов (HTTP-клиенты или блокировка базы)

Движок различает два повода — матчер лога смотрит обе формулировки, но
диагноз в `WARN` разный:

1. **HTTP-клиенты** — ИБ публикует не одна служба Apache. Скрипт гасит только
   `APACHE_SERVICE_NAME`, а вторая публикация (например, MCP на другом порту,
   служба `Apache24-2`) продолжает держать HTTP-сеансы — поэтому
   `/UpdateDBCfg` не может взять эксклюзивную блокировку. Остановка
   `APACHE_SERVICE_NAME` не помогает: файлы уже загружены, не применён только
   UpdateDB.
2. **Исключительная блокировка / активные сеансы** (не HTTP) — базу держит
   конфигуратор, `ibcmd` или длинная транзакция. `-SessionTerminate force`
   такую блокировку снимает **не всегда**, а сеансы пользователей при этом
   рвутся без пользы — на prod-базе это отдельное решение, не «ещё один retry».

Симптомы в логе:

```text
ОШИБКА: Обновление основной конфигурации базы данных завершилось с ошибкой (код: 1)
ОШИБКА:   Динамическое обновление конфигурации БД невозможно:
           обнаружены клиенты, работающие по HTTP
```

Тот же retry срабатывает и на «Ошибка исключительной блокировки информационной
базы … Активные сеансы» (матчер лога знает обе формулировки, плюс английские
`exclusive lock` / `active sessions`).

Причина (для HTTP-случая): ИБ публикует не одна служба Apache. Скрипт гасит только
`APACHE_SERVICE_NAME`, а вторая публикация (например, MCP на другом порту,
служба `Apache24-2`) продолжает держать HTTP-сеансы — поэтому
`/UpdateDBCfg` не может взять эксклюзивную блокировку. Остановка
`APACHE_SERVICE_NAME` не помогает: файлы уже загружены, не применён только
UpdateDB.

Рабочая команда (designer), проверено на 8.5.1.1302:

```bash
1cv8.exe CONFIG /F"C:/base/proj" /UpdateDBCfg -Dynamic- -SessionTerminate force /DisableStartupDialogs
```

Важно: `-SessionTerminate force` работает **только** вместе с `-Dynamic-`.
Без `-Dynamic-` платформа на динамическое/эксклюзивное обновление не идёт,
и ошибка по HTTP-клиентам повторяется.

Движок делает этот retry сам, если после `/UpdateDBCfg` в логе есть признак
конфликта сеансов (HTTP **или** исключительная блокировка) и разрешён гейт
`UPDATE_DB_FORCE_SESSIONS` (или явный `--force-sessions`). Сеансы завершаются
принудительно — в лог пишется `WARN`, что пользователи отключаются. На
prod-хостах гейт выключайте (`UPDATE_DB_FORCE_SESSIONS=false` /
`--no-force-sessions`): тогда скрипт упадёт с подсказкой, но никого молча не
разорвёт. Без второй публикации (и без ошибки сеансов) поведение не меняется.
Причина останова пишется и в `LOAD_HISTORY_REASON` (`… конфликт сеансов:
HTTP-клиенты …` / `… активные сеансы/исключительная блокировка …, force-терминация
не помогла`).

**База на автономном сервере (`IBSRV_PID_FILE`): дефолт `false`.**
`-SessionTerminate force` роняет `ibsrv.exe` в mdmp (04.11.2026): узел держит
сеансы сам, принудительное завершение уносит сервер. Пустое значение
(`UPDATE_DB_FORCE_SESSIONS=` в `.env`) считается **не заданным** — иначе
`.env` с пустым ключом включал бы force на ibsrv. Явное
`UPDATE_DB_FORCE_SESSIONS=true` по-прежнему уважается, но тогда сеансы снимайте
заранее (`ibcmd session list --pid=…` → `ibcmd session terminate …`).

### ibcmd

Аналог есть: у `ibcmd infobase config apply` ключи `--dynamic=<auto|disable|prompt|force>`
и `--session-terminate=<disable|prompt|force>` (по умолчанию `auto` и `disable`).
Retry движка для ibcmd:

```bash
ibcmd infobase config apply ... --force --dynamic=disable --session-terminate=force
```

### Мультислужбовый Apache

На Windows движок перед UpdateDB предупреждает, если в системе запущены другие
службы `Apache24*`/`*httpd*` кроме `APACHE_SERVICE_NAME`: они тоже публикуют ИБ
и держат HTTP-сеансы. Консьюмерский `tools/os/apache.sh` управляет одной службой;
список `APACHE_SERVICE_NAMES` пока не поддержан (будущее расширение).

Полный разбор «кто ещё может держать базу» (Apache, IIS, `ibsrv`, зависший
конфигуратор, клиентские и тестовые сессии) и рецепт «остановить → сделать →
поднять → проверить» — [infobase-exclusive-access.md](infobase-exclusive-access.md).

## Полная загрузка: флаки-спин и ретраи

Симптом: полная загрузка (`-F`, а также changeset с `Configuration.xml`) **залипает** —
сначала минуты живого I/O, затем CPU ~100% при **нуле** I/O, файл ИБ не меняется,
`/Out` пуст. Это не ошибка и не занятость: **флаки-гонка платформы**, а не свойство
дампа или монополии (проверено 26.09.2026: одна и та же `conf/` на пустой ИБ —
1 спин из 6 прогонов; на базе с расширениями спинит чаще, до 4/4 на отдельных файлах).

Что делать:

- запускать под `timeout` и **повторять 2–3 раза** — повтор обычно проходит;
- «жив или спинит» проверяется счётчиками процесса
  (`Get-CimInstance Win32_Process` → `ReadOperationCount`/`WriteOperationCount`)
  и mtime файла ИБ: спин = счётчики не растут, CPU не падает;
- **двухшаговый обход**, если спинит конкретный файл (в потребителе так вело себя
  `Roles/*/Ext/Rights.xml` на базе с расширениями): полная загрузка из дампа **без**
  этого изменения → затем **частичная** загрузка этого файла
  (`--list-file` + `SKIP_CONFIGURATION_CACHE=true`).

## Загрузка виснет молча: mdmp и счётчик [N/M]

Полная или changeset-загрузка может умереть **без сообщения**: `rc≠0`, stderr пуст,
`/Out` пуст или не создан, в логе прогресс стоит на последнем **успешном** файле.

Что смотреть по порядку:

1. **Счётчик `[N/M]`** в логе импорта не растёт 5–10 мин → парсер умер на
   конкретном файле, а не «нет памяти» и не лимит платформы.
2. **Крэш-дампы**: `%LOCALAPPDATA%\1C\1cv8\dumps\*.mdmp` (`ibcmd_*`, `1cv8_*`,
   `ibsrv_*`) — время файла даёт момент падения. Есть свежие дампы → нативная
   ошибка парсера, а не валидация метаданных.
3. **Виноватый файл** — почти всегда не тот, что показан последним (в прогрессе
   виден последний **обработанный**). Кандидатов ищет линтер потребителя:
   `python tools/metadata-xml-lint/check.py -q conf/`; иначе — бисект по списку
   (половина списка → повтор).

Типичная причина: объект не в формате дампа (inline-шаблон, нет
`Templates/<Имя>.xml`, `TemplateType` не по содержимому). Падение происходит на
этапе разбора, до проверок метаданных, поэтому `--no-check` и `-I` не помогают.

Дешёвый верификатор после успешного прогона: повторить
`ibcmd infobase config apply …` — ответ «Обновление конфигурации базы данных
не требуется» означает, что конфигурация в базе актуальна (без MCP и клиента).

## Долгая загрузка: фон и таймаут инструмента

Полный импорт `conf/` идёт 20–25 мин (полная пересборка 26.09.2026 — 25m48s).
Таймаут инструмента агента убивает **bash**, но не `1cv8`/`ibcmd`: процесс 1С
остаётся сиротой и продолжает держать базу, а EXIT-трап загрузчика его не
снимает (`SIGKILL` трап не выполняет; на `SIGINT`/`SIGTERM` он сработает и даже
поднимет Apache, но импорт-сирота продолжится). Запускай фоном и опрашивай:

```bash
mkdir -p .tmp
nohup ./load-changed-files.sh -U > .tmp/load.log 2>&1 &
echo $! > .tmp/load.pid
```

`.tmp/load.pid` — тот же bash (корневой wrapper делает `exec`), поэтому
`kill -0 $(cat .tmp/load.pid)` отвечает «прогон ещё жив». Прогресс импорта — не
в `.tmp/load.log` (там вывод движка и итог), а в `.tmp/load-changed-files.log`
(`/Out` конфигуратора, редирект у ibcmd) — по счётчику `[N/M]`.

- **Критерий «спинит»** — счётчики I/O процесса 1С и mtime файла ИБ, рецепт в
  разделе «Полная загрузка: флаки-спин и ретраи» (цифры не дублируем).
- **Не убивать слепо.** Сначала мягкая/штатная остановка (если инструмент умеет
  слать сигнал — им, `--signal`-подобный флаг), затем дождаться выхода процесса
  1С. Жёсткое убийство самого 1С — незавершённая операция и висячий сеанс
  конфигуратора, после неё путь один: `-F -U`. Своего `--signal`/`--abort`
  у движка нет.
- **Прогон доехал**: строка `Итого: <dur> | … | UpdateDB: да` в
  `.tmp/load.log`, последняя запись `.tmp/load-history.jsonl` с
  `"result":"ok"` и `"flags":{"update_db":true}`, плюс верификатор из раздела
  «Загрузка виснет молча».
- Фоном stdin неинтерактивный: промпт «закрыть конфигуратор?» недоступен
  (`exit 2`) — закрывай заранее или запускай с `--allow-close-designer`.
- Штатного `--detach`/`--watch` в движке **нет** (rg по
  `harness/tools/load-changed-files/` пуст) — фон только руками, как выше;
  самодетач движка — возможное будущее расширение.

## Кэш хешей conf: тихий пропуск файла

Скрипт ведёт манифест sha256 и пропускает файлы, чей хеш совпал с записанным.
Неверная запись манифеста **самоподдерживается**: файл пропускается, а
пост-обновление снова пишет его хеш — файл не загрузится уже никогда, а прогон
отчитается успехом. Лечение: `SKIP_CONFIGURATION_CACHE=true` (грузит перечисленное
без сверки с кэшем). Имена пропущенных файлов печатаются в логе
(`Кэш conf, пропущены: …`) — если правка не появилась в ИБ, смотри эту строку.

## Порядок элементов в Form.xml

Платформа читает `Form.xml` через XDTO со строгим порядком потомков (например,
в `InputField` сначала `DataPath`, потом `Title`). Нарушение порядка даёт
«Исключение XDTO при чтении файла» при partial-загрузке и **CPU-спин** при `-F`.
Штатный `form-validate` это **не** ловит (проверено 26.09.2026). Если у потребителя
есть свой корпус форм — полезен эмпирический чекер: для каждого типа родителя
считаем направление пар «A перед B» по всему `conf/` и ищем файлы, идущие против
сильного большинства.

## Чек-лист агента

1. Правки в git (`conf/`, `cfe.xml/`)? → без `--list-file`.
2. Не трогал `cfe.xml/` → `--no-extensions`.
3. `.env` настроен (`cp .env.example .env`).
4. Обычный load: `./load-changed-files.sh -U`. Merge + отставание ИБ: `-F -U`.
5. Не записывать маркер = текущий HEAD до успешной заливки файлов.
   При `--no-extensions` маркер пишется сам — если скипнутой ext-дельты
   не было (WARN объяснит, когда нет).
6. BSL/XML проверки до load — `/bsl-check`, `/xml-wellformed`.
