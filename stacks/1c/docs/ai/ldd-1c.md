# LDD — binding стека 1c

Реализация контракта [ldd.md](../../../../core/docs/ai/ldd.md) (core) на платформе
1С: запись в журнал регистрации, маппинг уровней, triage. Имена обёрток и
префиксы событий конкретного потребителя — в его addendum, не здесь.

> **Граница.** «Когда и как логировать» — runtime-правила, канон
> [logging-strategy.md](../../../../core/docs/ai/logging-strategy.md) (core).
> Транзакционный контекст — [locks-and-transactions.md](locks-and-transactions.md).

## 1. Запись

- Обёртка потребителя, если есть; иначе `ЗаписьЖурналаРегистрации`.
- Запись — **транзакционно-независимая** (переживает откат): лог операции не
  должен пропадать вместе с откаченной транзакцией.
- `Данные` = **ссылки** на сущности (отбор по объекту в журнале), не `Структура`.

## 2. Имя события

Generic `<домен>.<операция>` → `ИмяСобытия` журнала:

```text
<Потребитель>.<Тема>.<Операция>
```

Префикс потребителя может добавлять обёртка автоматически — тогда в вызове без
него. Суффикс исхода — как в core: опционален, уровень несёт исход.

## 3. Маппинг уровней

| Generic (спека) | Журнал регистрации |
| --- | --- |
| ERROR | `УровеньЖурналаРегистрации.Ошибка` |
| WARN | `УровеньЖурналаРегистрации.Предупреждение` |
| INFO | `УровеньЖурналаРегистрации.Информация` |
| DEBUG | не журнал — отладчик; до коммита убрать |

## 4. Correlation id

GUID операции в комментарии записи или в `Данные` (если ссылка-носитель есть).
Один GUID сквозь всю цепочку многошагового сценария.

## 5. Triage gate

Перед «готово» прочитать журнал регистрации прогона и сверить с таблицей спеки:

- HTTP MCP-сервер потребителя с tool чтения ЖР — если опубликован;
- консоль/журнал регистрации в предприятии;
- выгрузка ЖР в XML для офлайн-разбора.

## 6. Алерты

Встроенного канала нет — внешний watchdog по журналу регистрации или
регламентное задание-монитор. Объявляется в спеке только если у потребителя
такой контур есть.
