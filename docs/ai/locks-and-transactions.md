# Блокировки и транзакции — правила проектирования

В платформе 1С две подсистемы блокировок (автоматическая / управляемая) и модель
неявных транзакций вокруг записи объектов. Большинство инцидентов в проде — из
смешения режимов, неявных транзакций и удержания блокировок поверх диалогов с
пользователем. Здесь — канонические правила.

> **Граница.** Эта дока — дизайн-правила. Узкий кейс «поставить блокировку до
> чтения остатков при проведении» — рабочий пример в
> [platform-pitfalls.md](platform-pitfalls.md) (раздел «Управляемые блокировки»);
> оттуда — сюда за общей теорией.

## 1. Режим блокировки конфигурации

Свойство конфигурации **«Режим управления блокировкой данных»** — `Управляемый`
для всей конфигурации. Причины:

- Смешанный режим прячет баги — код, написанный под автоматическую блокировку,
  внезапно конфликтует на том же пути данных под управляемой.
- Управляемый режим — единственный, где гранулярность блокировок под контролем
  разработчика (по таблице / ключу, а не по странице строк).
- Современные подсистемы БСП рассчитывают на управляемый режим.

Проект на `{PLATFORM_BUILD}` — режим уже управляемый. Перевод существующего
проекта с автоматического на управляемый — отдельная многошаговая задача (ИТС
«Перевод конфигурации на управляемый режим блокировки»), здесь не описана.

## 2. Границы транзакций

### Неявные транзакции

Платформа сама открывает транзакцию вокруг:

- `Записать()` объекта ссылки — обёртывает **`ПередЗаписью` → запись → `ПриЗаписи`
  → проведение (`ОбработкаПроведения`)**.
- `Удалить()` объекта ссылки.
- `НаборЗаписей.Записать()` для наборов записей регистров.
- Материализация движений в конце `ОбработкаПроведения`.

**Внутри `ПередЗаписью` / `ПриЗаписи` / `ОбработкаПроведения` НЕ открывай свою
`НачалоТранзакции` / `ЗафиксироватьТранзакцию`.** Транзакция уже есть; вложенный
вызов создаёт точку сохранения, но ломает откат внешней ошибки.

### Явные транзакции в вызывающем коде

Когда надо атомарно записать несколько объектов или совместить запись с правками
регистров — открывай транзакцию в вызывающем коде:

```1c
НачалоТранзакции();

Попытка
    Документ.Записать(РежимЗаписиДокумента.Проведение);
    // ... прочие изменения ...
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();

    ДанныеОшибки = Новый Структура;
    ДанныеОшибки.Вставить("Документ", Документ.Ссылка);
    ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));

    ОбёрткаЖурналаОшибка(
        "Проведение." + Документ.Метаданные().Имя + ".Ошибка",
        НСтр("ru = 'Не удалось провести документ.'"),
        ДанныеОшибки);

    ВызватьИсключение;
КонецПопытки;
```

Логирование ошибок — через обёртку журнала потребителя (канон
`code-standards.md` в репо потребителя, § логирование), не через сырой
`ЗаписьЖурналаРегистрации`. Структурированные данные (`Данные = Структура`) —
не склеивай контекст в одну строку.

Правила:

- Шаблон `НачалоТранзакции()` → `Попытка` … `ЗафиксироватьТранзакцию()` →
  `Исключение` `ОтменитьТранзакцию()` `ВызватьИсключение` `КонецПопытки` —
  **единственный** правильный. Любое отклонение (нет `Попытки`, нет
  `ОтменитьТранзакцию` в ветке исключения, нет перевыброса) — дефект.
- **Диагностируй, не глотай.** Запиши ошибку в журнал и `ВызватьИсключение`.
- `ТранзакцияАктивна()` перед повторной `ОтменитьТранзакцию` — только в
  диагностике; в нормальном потоке гарантировано и так.

### Запрещено внутри транзакции

- **Диалоги с пользователем** (`ВопросАсинх`, `ПоказатьЗначение`, выбор файла).
  Любое ожидание ввода держит блокировки и встаёт другими сессиями. См.
  [async-methods.md](async-methods.md).
- **Длительные операции** (`ДлительныеОперации`, сетевые вызовы, внешние
  компоненты). Выноси за пределы транзакции.
- **`ЗаписьЖурналаРегистрации` с `Сообщить`** в клиентском контексте — сообщение
  уходит в UI, заблокированный за транзакцией.

## 3. Примитивы управляемых блокировок

Блокируй управляемые данные через `БлокировкаДанных`:

```1c
Блокировка = Новый БлокировкаДанных;

ЭлементБлокировки = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
ЭлементБлокировки.Режим = РежимБлокировкиДанных.Исключительный;
ЭлементБлокировки.ИсточникДанных = Товары;
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Склад",       "Склад");

Блокировка.Заблокировать();
```

Правила:

- **Блокируй до чтения**, затем читай, затем пиши. Чтение без блокировки с
  последующей записью оставляет окно, в котором параллельное проведение пишет
  несогласованные остатки.
- **Блокируй регистр, а не документ.** Блокировка документа не защищает
  регистр; следующее проведение всё равно прочитает устаревшие остатки.
- **`ИсточникДанных`, не ручная итерация.** Передавай табличную часть документа
  (или `ТаблицаЗначений` из неё) как `ИсточникДанных` и мапь колонки через
  `ИспользоватьИзИсточникаДанных` — платформа соберёт один эффективный запрос
  блокировки.
- **Блокировка живёт до конца текущей транзакции.** Раньше освободить нельзя —
  можно только завершить транзакцию.

### Режимы

| `РежимБлокировкиДанных` | Для чего |
| --- | --- |
| `Исключительный` | Чтение-изменение-запись: проведение, массовая запись. Блокирует читателей и писателей. |
| `Разделяемый` | Согласованное чтение в транзакции (отчёт по нескольким регистрам). |

Разделяемые блокировки совместимы между собой; исключительная против
разделяемой — ждёт. `Разделяемый` не защищает от параллельных писателей, а лишь
мешает им подняться до исключительного, пока ты читаешь.

По умолчанию — `Исключительный` для любого пути записи. `Разделяемый` —
осознанно, только для согласованных чтений.

## 4. Порядок блокировок — контракт от дедлоков

Для дедлока нужны две транзакции, берущие блокировки в разном порядке. Фикс —
**зафиксировать порядок блокировок на весь проект**.

Установи канонический порядок блокируемых таблиц и зафиксируй в `memory.md` как
правило проекта. Пример для типовой конфигурации продажи-склад:

```text
1. РегистрНакопления.ТоварыНаСкладах
2. РегистрНакопления.ТоварыКПередаче
3. РегистрНакопления.СвободныеОстатки
4. РегистрСведений.ЦеныНоменклатуры
5. РегистрНакопления.ВзаиморасчетыСКонтрагентами
```

Правила:

- Каждое проведение, затрагивающее больше одного регистра из списка, блокирует
  их в указанном порядке. Без исключений.
- Новые регистры в порядок — **добавляй в конец**, не вставляй в середину
  (перенумерация ломает существующие ревью).
- Междокументные операции (один документ проводит другой) наследуют тот же
  порядок — вызывающий код берёт блокировки в каноническом порядке, затем
  вызывает подчинённые операции.

Если ловишь дедлок под нагрузкой, вопрос не «как сделать retry», а «какая
транзакция взяла блокировки не в том порядке». Чини порядок; retry — пластырь.

## 5. Паттерны блокировок

### Проведение документа по нескольким регистрам

```1c
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

    // 1. Собери объект блокировки один раз, в каноническом порядке.
    Блокировка = Новый БлокировкаДанных;

    БлокТовары = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
    БлокТовары.Режим = РежимБлокировкиДанных.Исключительный;
    БлокТовары.ИсточникДанных = Товары;
    БлокТовары.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
    БлокТовары.ИспользоватьИзИсточникаДанных("Склад", "Склад");

    БлокВзаиморасчеты = Блокировка.Добавить("РегистрНакопления.ВзаиморасчетыСКонтрагентами");
    БлокВзаиморасчеты.Режим = РежимБлокировкиДанных.Исключительный;
    БлокВзаиморасчеты.УстановитьЗначение("Контрагент", Контрагент);

    Блокировка.Заблокировать();

    // 2. Чтение остатков и валидация.
    // 3. Запись движений через Движения.X.Добавить / Записать = Истина.

КонецПроцедуры
```

### Массовая операция по множеству документов

Если нужна атомарность между документами — веди транзакцию в вызывающем коде, а не
по каждому документу. Иначе оборачивай каждый документ в свою транзакцию и
продолжай по неудачам (логируя каждую) — выбор по бизнес-требованию.

Никогда не держи одну транзакцию по тысячам документов — эскалация блокировок и
давление на журнал журнала калечат кластер.

### Обновление статуса вне проведения

Для регистров сведений как журнала статусов (`СтатусыЗаказов`, `СтатусыИнтеграции`)
— запись набора записей с `НаборЗаписей.Заблокировать()` в явной транзакции:

```1c
НачалоТранзакции();

Попытка

    НаборЗаписей = РегистрыСведений.СтатусыИнтеграции.СоздатьНаборЗаписей();
    НаборЗаписей.Отбор.Заказ.Установить(СсылкаЗаказа);
    НаборЗаписей.Заблокировать();
    НаборЗаписей.Прочитать();

    // ... мутация набора ...

    НаборЗаписей.Записать();
    ЗафиксироватьТранзакцию();

Исключение
    ОтменитьТранзакцию();
    ВызватьИсключение;
КонецПопытки;
```

`НаборЗаписей.Заблокировать()` — удобная форма управляемой блокировки в рамках
отбора набора; используй, когда вся суть — «собираюсь переписать эти записи».

## 6. Диагностика конфликтов и дедлоков

### Симптомы

- *«Конфликт блокировок при выполнении транзакции»* — спорадический таймаут на
  регистре; причина: другая транзакция держит тот же ключ в несовместимом режиме
  дольше `MaxLockWait` (по умолчанию 20 с).
- *«Deadlock»* — две транзакции ждут друг друга; причина: нарушен порядок
  блокировок (§4).
- *«Запись регистра не удалось получить»* при проведении — обычно конфликт
  блокировок на регистре, а не на наборе записей.

### Инструменты

- **Технологический журнал (`logcfg.xml`)** — включи события `TLOCK` и
  `TDEADLOCK` для проблемного регистра. Журнал фиксирует, кто что держит и что
  ждёт. Единственный авторитетный источник «какие две транзакции сдедлокнулись».
- **`ТранзакцияАктивна()`** — проверка, что текущая транзакция жива; полезна
  только для самопроверок, не для кросс-сессионной диагностики.
- **DMV MS SQL (для серверной ИБ)** — `sys.dm_tran_locks`,
  `sys.dm_os_waiting_tasks` для живых снапшотов, когда техжурнала не хватает.
- **Воспроизведение проведения** — перепроведи падающий документ под отладчиком,
  чтобы поймать точную последовательность вызовов блокировок.

Методологию — см. [systematic-debugging.md](systematic-debugging.md) (в планах
добавления): блокировки диагностируются в порядке Reproduce → Hypothesize →
Experiment → Fix, а не угадыванием с retry.
