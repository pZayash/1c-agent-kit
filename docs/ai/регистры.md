# Регистры — проектирование

Регистры — каркас любой нетривиальной конфигурации 1С; ошибки здесь дороги
откатом, т.к. обычно вшиты в проведение документов, RLS и отчёты. Здесь —
дизайн-решения, которые стоит продумать **до** запуска скилла `meta-*`.

> **Граница.** Эта дока — *дизайн* регистров. XML/механика объектов — скиллы
> `meta-compile`/`meta-edit`/`meta-info`. Запросы по регистрам —
> [query-standards.md](query-standards.md) (и скилл `1c-query-rule`). Блокировки
> при проведении — [locks-and-transactions.md](locks-and-transactions.md).
> Отчёты по регистрам (СКД) — [скд.md](скд.md).

## 1. Выбор типа регистра

| Тип регистра | Когда |
| --- | --- |
| **РегистрСведений** | Произвольные табличные данные, индексированные измерениями, с опц. периодичностью. |
| **РегистрНакопления («Остатки»)** | Остатки на момент (склад, долг, распределение). «Сколько сейчас / на дату X». |
| **РегистрНакопления («Обороты»)** | Обороты по периодам, никогда не спрашиваются как остаток (продажи, трафик). |
| **РегистрБухгалтерии** | Двойная запись с планом счетов. |
| **РегистрРасчета** | Зарплата / пересчёт по периодам с зависимостями видов начислений. |

Read-modify-write для `РегистрСведений`: настройки, маппинги, кэш-справочники,
исторические значения реквизитов, статус обмена, статус длительной операции.

Когда избегать:

- **Сведений** — данные **дельта**, суммируемая в остатки/обороты → накопление.
- **Накопления «Остатки»** — нужны только обороты по периодам, без вопроса остатка → «Обороты» или регистр сведений.
- **Накопления «Обороты»** — вопрос остатка реалистичен; потеря остатков = полный редизайн.
- **Бухгалтерии** — «двойная запись» притянута → лучше накопление.
- **Расчета** — всё, что не зарплата/пересчёт по периодам.

Модель по умолчанию: *«может ли пользователь спросить остаток на дату?»* →
накопление. *«это просто типизированный индексированный справочник?»* → регистр
сведений. Иначе — подумать ещё, не начинать с бухгалтерского/расчетного по инерции.

## 2. Измерения

- **Кардинальность — первой.** Высококардинальные, узкофильтруемые измерения —
  вперёд (`Контрагент`, `Договор`, `Номенклатура`); низкокардинальные
  (`Организация`, `Подразделение`) — после. Порядок влияет на использование
  индексов в запросах по виртуальным таблицам.
- **Стабильная идентичность, не свободный текст.** Измерения — ссылочных типов
  (`СправочникСсылка.X`, `ДокументСсылка.X`, `Перечисление.X`, `Дата` для
  периодических). Строки/числовые коды как измерения — антипаттерн: данные
  форкаются на каждой опечатке.
- **Периодичность.** Выбирай самую грубую, что ещё отвечает бизнес-вопросу:
  `НеПериодический` (константы, маппинги, текущие значения реквизитов),
  `ВПределахСекунды` (движения по умолчанию), `ВПределахДня` (курсы, лог статусов),
  `ВПределахМесяца` / `Год` (планирование). Более мелкая периодичность раздувает
  таблицу и замедляет всё.
- **`Ведущее` (Leading)** — ставить на измерение, удаление которого должно
  каскадно удалить запись регистра (например `Ведущее` на `Контрагент` — записи
  удалённого контрагента исчезают). **Не** ставить `Ведущее` по умолчанию —
  большинство измерений не ведущие.

## 3. Ресурсы

- **Ресурсы — числовые/количественные.** Для накопления — **должны** быть
  суммируемыми (`Количество`, `Сумма`, `КоличествоСтрок`). Для сведений — любой
  тип, но это «значение по ключу измерений».
- **Один ресурс — одна единица.** Смешивать `Сумму` (в разных валютах) в один
  ресурс — ловушка. Либо дробить по ресурсам на валюту, либо валюта — измерение.
- **Отрицательные значения.** Для накопления — допустимы и осмысленны (возвраты,
  списания). Для сведений — обычно code smell, кроме явно знаковых сумм.

## 4. Реквизиты

- Реквизиты — неагрегируемые, нефильтруемые данные, travelling с записью
  (`Комментарий`, `НомерЗаказа`). По умолчанию не индексируются; **не** фильтровать
  запросы по полям-реквизитам в горячих путях.
- Если по реквизиту фильтруешь постоянно — повышай до измерения.

## 5. Индексирование

- `Индексировать` у измерения — только если оно участвует в запросах/параметрах
  виртуальных таблиц **без** всех предшествующих измерений. Первое измерение не
  требует явного индекса — платформа строит.
- Для регистров сведений, используемых как lookup по подмножеству не-ведущих
  измерений — помечай `Индексировать` именно это подмножество. Не «индексировать
  всё на всякий случай» — каждый индекс тормозит запись.
- Регистры бухгалтерии — особое индексирование, см. ITS.

## 6. Подчинение регистратору (накопление / бухгалтерия / расчет)

- **`Подчинение регистратору`** — по умолчанию для накопления; регистр питается
  движениями документа через `ОбработкаПроведения`.
- **`Независимый`** регистр сведений без регистратора — для данных без
  документа-источника (настройки, маппинги, текущие значения).
- **Смешанный режим доступа** у регистра сведений (`Независимый` с регистратором)
  — иногда полезен для логов статусов; считать продвинутым, обосновать в ТЗ.

## 7. Остатки, обороты, срезы

При наличии остатков платформа даёт виртуальные таблицы:

| Таблица | Назначение |
| --- | --- |
| `Остатки(&Период, Условие)` | Остаток на `&Период` по фильтру. |
| `Обороты(&НачалоПериода, &КонецПериода, ..., Условие)` | Обороты за период. |
| `ОстаткиИОбороты(...)` | Нач. остаток + оборот + кон. остаток одним заходом. |
| `СрезПервых(&Период, Условие)` (сведений) | Первая запись на/после даты. |
| `СрезПоследних(&Период, Условие)` (сведений) | Последняя запись на/до даты. |

**Фильтровать виртуальные таблицы через параметры, не через `ГДЕ` после вызова**
— твёрдое правило (см. [query-standards.md](query-standards.md)). Фильтр в
параметре пушится в движок и использует индексы; фильтр в `ГДЕ` читает всю
виртуальную таблицу.

## 8. Проведение / перепроведение

- **`ОбработкаПроведения`** — в модуле объекта документа. Внутри: блокировка,
  чтение, запись (см. [locks-and-transactions.md](locks-and-transactions.md)). Без
  пользовательских диалогов, длительных операций, внешних сервисов.
- **`Движения.X.Записывать = Истина`** — управляет записью in-memory ТЧ в регистр
  на коммите. Поставь один раз; не тогглить в циклах.
- **Не модифицировать движения вне `ОбработкаПроведения` /
  `ОбработкаУдаленияПроведения`.** Прямая манипуляция `Движения.X` из внешнего
  кода (обработка) обходит логику последовательностей и создаёт неконсистентные
  данные.
- **Перепроведение** (`ОбработкаЗаполнения` — не то). Для массового
  перепроведения: `Документы.X.Выбрать()` + `Записать(РежимЗаписиДокумента.Проведение)`
  в цикле транзакция-на-документ с явной отменой по ошибке.
- **`Последовательности`** — когда порядок документов между документами важен
  (отгрузка раньше оплаты и т.п.), заводи `Последовательность`, а не полагайся на
  порядок вставки.

## 9. Запросы по регистрам

- **Всегда виртуальные таблицы** для остатков/оборотов. Не сворачивай свою
  агрегацию по физической таблице.
- **Индексируй фильтры по измерениям в метаданных**, не в BSL.
- **`ВЫБРАТЬ ПЕРВЫЕ 1 ... УПОРЯДОЧИТЬ ПО ... УБЫВ`** как «последнее значение» —
  ок для непериодического регистра сведений; для периодического — `СрезПоследних`.
- **Агрегаты.** Для накопления `ВклАгрегаты` и `АгрегатыЭтоПлоский` могут уже
  ускорять запрос; не отключать агрегаты без замера.

## 10. RLS

- Ограничения доступа к регистру — как у справочников/документов.
- Для регистров, джойнящих несколько типовых объектов через измерения, шаблон
  ограничения может разрастись — выноси повторяющиеся `И`-условия в переиспользуемый
  предикат через подсистему БСП управления доступом.
- Тестируй ограничение под не-админской ролью перед merge — админ обходит RLS и
  прячет баги. Права новых объектов — роль базовых прав потребителя (см.
  [object-conventions.md](object-conventions.md), § права доступа).
