# Формат ROLES

`ROLES.md` (корень потребителя) — **библиотека ролей сотрудников и контрагентов**:
кто участвует в процессах, что делает, чем отличается от похожих ролей.
Наполняется в [/explore](../../cursor/skills/explore/SKILL.md) по аналогии с
`CONTEXT.md` (словарь домена), но описывает **людей и их функции**, не термины.

Назначение: каталог ролей для аналитики задач (кто постановщик, кого затронет
изменение, кто согласует).

## Когда создавать

- Лениво: при **первой** роли, выясненной в /explore.
- Один `ROLES.md` в корне (single-context). При мульти-контексте — рядом с
  соответствующим `CONTEXT.md`.
- Дополнять inline по ходу диалога, не батчить «на потом».

## Связь со спеками (инвариант)

- Любая роль, упомянутая в спеке (`proposal.md`, `design.md`, `spec.md`),
  **обязана** быть в `ROLES.md`.
- В спеке — ссылка/имя роли; **полное определение** — только в `ROLES.md`.
- **Актор сценария** в `spec.md` (ДАНО/КОГДА/ТОГДА, строка `ДАНО <актор>…`):
  если действующее лицо — реальная бизнес-роль, каноничное имя из `ROLES.md`.
  Родовой `пользователь` / `Система` / `пользователь ИБ U` ролью **не** оформлять —
  спеки системо-центричны (`Система MUST…`), не user-story «Как [роль], я хочу…».

## Шаблон

```md
# Роли проекта

Библиотека ролей сотрудников и контрагентов: функции, отличия, типичное участие
в задачах. Канон имени роли — один на роль.

## Roles

**Менеджер по продажам**:
Оформляет коммерческие предложения и заказы, общается с клиентом по счёту.
_Тип_: сотрудник.
_Участие_: частый постановщик задач по печати и ценообразованию.
_Avoid_: «продавец», «оператор» (оператор — кто ведёт чат, не роль в процессе).
_Статус_: согласовано.

**Бухгалтер**:
Ведёт учёт по организации, отвечает за обмен с внешней учётной системой.
_Тип_: сотрудник.
_Связи_: термин обмена в CONTEXT.md.
_Avoid_: путать с юрлицом (это не роль).
_Статус_: предположено.

## Relationships

- **Менеджер по продажам** инициирует задачу → **Бухгалтер** согласует учётную часть.

## Flagged ambiguities

- «Оператор» использовался и как роль в процессе, и как тот, кто ведёт чат —
  разведено: оператор чата ≠ роль сотрудника.
```

## Поля записи роли

- **Заголовок** — каноничное имя роли (одно на роль).
- Одно предложение — что роль делает (функция), не «кто это вообще».
- `_Тип_` — `сотрудник` / `клиент` / `контрагент` / `система`.
- `_Участие_` (опц.) — постановщик / исполнитель / согласующий / затронут.
- `_Связи_` (опц.) — роли доступа ИБ, профили, термины `CONTEXT.md`.
- `_Avoid_` — запрещённые синонимы и частые путаницы.
- `_Статус_` — `согласовано` (подтвердил оператор) / `предположено` (агент, ждёт).

## Эволюция ролей

`ROLES.md` живой:

- **Изменить существующую роль** — новые обязанности: обновить запись.
  Согласования не требует; существенный сдвиг смысла — отметить и подтвердить.
- **Объединить или разделить** — только по согласованию с оператором.
- При объединении — старые имена в `_Avoid_`; при разделении — в
  `Flagged ambiguities`.

## Правила

- Один каноничный термин на роль; конфликты — в `Flagged ambiguities`.
- Роли доступа 1С (префикс потребителя) — **права в ИБ**, живут в `CONTEXT.md`.
  В `ROLES.md` — **бизнес-роли людей**; связь — поле `_Связи_`.
- Агент выбрал сам — `_Статус_: предположено`, пока оператор не подтвердил.
- Определения короткие: функция, не биография.
- **Роль ≠ должность ≠ персоналия.** Люди / штатка / процессы вне конфигурации —
  [ANALYTICS-FORMAT.md](ANALYTICS-FORMAT.md). В роли — `_Исполнитель_` на
  персоналию, не дублировать должность.
