# СКД — проектирование отчётов

Схема компоновки данных (`СхемаКомпоновкиДанных`, СКД) — канонический движок
отчётов 1С. Здесь — дизайн-правила, повторяющиеся в ревью. XML/механика `.dcs`
файлов — в скилле `skd-*` (`.cursor/skills/skd-compile` и др. в потребителе).
Антипаттерны медленных запросов внутри СКД — [query-standards.md](query-standards.md)
и `anti-patterns.md` (в планах добавления).

> **Граница.** Эта дока — общий дизайн СКД. Проектный паттерн «кодовый отчёт»
> (пустая СКД + вывод кодом в `ПриКомпоновкеРезультата`) — отдельная дока
> [код-отчёты.md](код-отчёты.md). Здесь — про живую схему.

## 1. Выбор типа набора данных

| Тип набора | Когда |
| --- | --- |
| **Запрос** | По умолчанию. Данные в метаданных, запрос выражает нужное. |
| **Объединение** | Комбинирование независимых запросов с одинаковой формой колонок (движения + остатки). |
| **Объект** | Данные из BSL как `ТаблицаЗначений` (внешняя система, агрегация, процедурная таблица). |

`Объект` использовать умеренно — теряется pushdown индексов и параметров.

По умолчанию — **Запрос** для всего, что выражается запросом. **Объединение** —
когда формы действительно совпадают. **Объект** — когда запросом не выразить.

## 2. Вычисляемые поля vs ресурсы vs поля запроса

Три разных механизма — выбирай по **моменту материализации**, не по «удобству
набора».

| Механизм | Когда считается | Для чего |
| --- | --- | --- |
| **Поле запроса** | Один раз, на СУБД при выполнении запроса | Всё, что СУБД может вычислить. Предпочтительно. |
| **Ресурс** | При агрегации, на итогах движка | Величины для суммирования/усреднения/счёта по группировкам. |
| **Вычисляемое поле** | По строкам, после выдачи строки | Построчные производные (представление, конкатенация). |

Ресурс участвует в итогах, вычисляемое поле — нет (кроме через `Вычислить()`).

Порядок предпочтения: **поле запроса → ресурс → вычисляемое поле**. Чем больше
вычислено в запросе, тем меньше строк движок тянет на клиент.

Антипаттерн: агрегация в **вычисляемом поле** через `Вычислить("Сумма(...)")` —
теряются индексы, полный скан строк. Используй **ресурс**.

## 3. Параметры

- **`Параметр` vs `ПараметрВыбора`.** `Параметр` привязан к запросу/набору;
  `ПараметрВыбора` — UI-фильтр выбора пользователя. Не взаимозаменяемы.
  `Параметр` — для входов запроса (`&Период`); `ПараметрВыбора` — для ограничения
  выбора в поле.
- **Периодичность виртуальных таблиц** (`Остатки(&Период, ...)`,
  `ОстаткиИОбороты(&НачалоПериода, &КонецПериода, ...)`) — **всегда** через
  параметры, не литералы дат в тексте запроса.
- **`Доступен`** — `Ложь` для параметров, вычисляемых программно (текущий
  пользователь, текущая дата), которые пользователь не должен править.
- **`Использование`** — `ВсегдаИспользовать` только для параметров, которые
  реально не могут быть пустыми; иначе `Авто`, чтобы движок мог выкинуть
  неиспользуемые параметры из плана.

## 4. Варианты и настройки

- **Варианты** — *разные формы отчёта*, не пользовательские фильтры. Дробить
  фундаментально разные представления одного отчёта («по документам» vs «по
  контрагентам»). Вариант «тот же отчёт с другим дефолтным фильтром» — неправильно;
  для этого есть пользовательские настройки.
- **Пользовательские настройки** (`Настройки пользователя`) — держи набор
  минимальным. Каждая настройка = контракт поддержки. Сокращай поверхность:
  - всё, что не пользовательская ручка, — `Недоступен`;
  - `БыстрыеНастройки` для 3–5 полей, которые пользователь реально меняет;
  - дефолт `Авто` вместо пустых значений для `Период`, `Организация` и т.п.

## 5. Программный override композиции

Для нетривиальных отчётов канон — **программный override**, а не правка схемы
под каждый вариант. Точки (по приоритету):

1. **`ПриКомпоновкеРезультата`** (модуль объекта отчёта) — предпочтительно.
   Модификация композиции до/после штатного компоновщика.
2. **`ПриЗагрузкеПользовательскихНастроекНаСервере` /
   `ПриЗагрузкеНастроекНаСервере`** — программная инъекция настроек (фильтры,
   параметры) при загрузке формы.
3. **`КомпоновщикНастроек.Настройки`** — прямая манипуляция деревом настроек.

Шаблон программной инъекции фильтра (полный — обработка ошибок, структурированное
логирование, без двойного вывода на штатном обработчике):

```1c
Процедура ПриКомпоновкеРезультата(ДокументРезультат, ПараметрыВывода, СтандартнаяОбработка)

    // Свой вывод; платформа НЕ должна запускать дефолтную компоновку.
    СтандартнаяОбработка = Ложь;

    КомпоновщикНастроек.ЗагрузитьНастройки(СхемаКомпоновкиДанных.НастройкиПоУмолчанию);
    УстановитьПараметр("Период",    ПериодОтчета);
    УстановитьФильтр("Организация", Организация);

    Попытка

        МакетКомпоновки = Новый КомпоновщикМакетаКомпоновкиДанных().Выполнить(
            СхемаКомпоновкиДанных, КомпоновщикНастроек.Настройки, , ,
            Тип("ГенераторМакетаКомпоновкиДанных"));

        ПроцессорКомпоновки = Новый ПроцессорКомпоновкиДанных;
        ПроцессорКомпоновки.Инициализировать(МакетКомпоновки);

        ПроцессорВывода = Новый ПроцессорВыводаРезультатаКомпоновкиДанныхВТабличныйДокумент;
        ПроцессорВывода.УстановитьДокумент(ДокументРезультат);
        ПроцессорВывода.Вывести(ПроцессорКомпоновки);

    Исключение

        ДанныеОшибки = Новый Структура;
        ДанныеОшибки.Вставить("Отчет",    Метаданные().Имя);
        ДанныеОшибки.Вставить("Период",   ПериодОтчета);
        ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));

        ОбёрткаЖурналаОшибка(
            "Отчет." + Метаданные().Имя + ".Ошибка",
            НСтр("ru = 'Не удалось сформировать отчет.'"),
            ДанныеОшибки);

        ВызватьИсключение;

    КонецПопытки;

КонецПроцедуры
```

Заметки:

- `СтандартнаяОбработка = Ложь` — **до** `Попытка`. Если обработчик вылетит через
  `ВызватьИсключение` посреди рендера, платформа не должна молча откатиться к
  дефолтной компоновке и выдать недоделанный второй документ.
- Логирование — через обёртку журнала потребителя (не сырой
  `ЗаписьЖурналаРегистрации`). Стандарты — `code-standards.md` в репо потребителя;
  точечное имя `Отчет.<Имя>.Ошибка`, структурированные `Данные = Структура`,
  `ПодробноеПредставлениеОшибки` (не `КраткоеПредставлениеОшибки`), перевыброс.
- `УстановитьПараметр` / `УстановитьФильтр` — проектные хелперы; вынеси их в модуль
  менеджера отчёта, чтобы override оставался компактным.

## 6. Взаимодействие с RLS

- Запросы СКД по умолчанию идут под ролями пользователя; `ОграничениеДоступа`
  задействованных объектов метаданных применяется.
- Если отчёт намеренно требует полной видимости (регуляторные отчёты для
  бухгалтерии/зарплаты), оберни компоновку в
  `УстановитьПривилегированныйРежим(Истина)` **только** в
  `ПриКомпоновкеРезультата`, и всегда парно с
  `УстановитьПривилегированныйРежим(Ложь)` в `Попытка`/`КонецПопытки`, даже если
  внутренний код считается безопасным. Обоснование — комментарием в строку.
- Не расширяй видимость молча — каждое использование привилегированного режима
  оправдано в описании отчёта/ТЗ.

## 7. Чек-лист производительности

- **Индексные поля фильтра** — каждый параметр, уходящий в `ГДЕ` запроса, должен
  попадать в индекс. Проверить: «Анализ производительности» в Конфигураторе или
  `ПолучитьСтруктуруХраненияБазыДанных`.
- **Виртуальные таблицы** — фильтруй через параметры
  (`Остатки(&Период, Условие)`), не через `ГДЕ` после виртуального вызова.
  Твёрдое правило (см. [query-standards.md](query-standards.md)).
- **`ПЕРВЫЕ N`** для пагинированных/top-N отчётов — пушь лимит в запрос, не в
  хук форматирования строк.
- **Не `ВЫРАЗИТЬ` слева в `ГДЕ`** — отключает использование индекса.
- **`Объект`-наборы**, тянущие большую `ТаблицаЗначений` из BSL — частая ловушка
  производительности; если данные переиспользуются, материализуй во временный
  регистр сведений.
