# Загрузка конфигурации в dev-ИБ (для агентов)

## Канон

Залить изменения из git (`conf/`, `cfe.xml/`) в **dev-базу** — только:

```bash
./load-changed-files.sh
```

С обновлением структуры БД после правок метаданных:

```bash
./load-changed-files.sh -U
```

Навык: **`/load-changed-files`**.

Ядро скрипта — `harness/tools/load-changed-files/` (kit). Корневой
`load-changed-files.sh` потребителя — thin wrapper.

Настройки: `.env` (`IB_CONNECTION`, `DESIGNER_PATH`, `CONFIG_PATH`,
`EXTENSIONS_PATH`). Шаблон ключей: [templates/env.example](../../templates/env.example).

Остановка публикации нужна только для **файловой** ИБ (`IB_CONNECTION=/F…`): её
держит worker Apache (`wsap24.dll`). Для серверной (`/S…`) и для автономного
сервера (`ibsrv` + `IBSRV_PID_FILE`) скрипт Apache не трогает.

Зависимости потребителя (не в kit): `tools/load-project-env.sh`, `tools/os/`.

## Не использовать

Upstream cc-1c: `db-load-git`, `db-load-xml`, `db-update`, `db-load-cf` —
исключены из sync. Канон — `./load-changed-files.sh`.

## Типовые флаги

- **`-U`** — `/UpdateDBCfg` после загрузки (почти всегда после метаданных).
- **`--no-extensions`** — только `conf/`, без `cfe.xml/`. **Обязателен**, если
  агент не менял расширения (защита от чужих правок в worktree).
- **`--list-file PATH`** — фолбэк: явный список вместо git-discovery.
- **`-F` / `--full-resync`** — вся `conf/` без partial; когда ИБ отстала от
  диска после merge («Неизвестный объект», exit 21).
- **`--reset-marker`** — удалить файл маркера (мёртвый SHA). **Не** канон
  «залить merge»: на чистом дереве это был бы только UpdateDB; скрипт на
  merge-HEAD сам берёт `HEAD^1`.
- **`--force-partial`** — не отменять partial с `Configuration.xml` после merge.
- **`--ibcmd`** / `LOAD_ENGINE=ibcmd` — headless/CI (медленнее designer).
  **Автономный сервер (`IBSRV_PID_FILE` задан):** тот же движок идёт через шлюз
  администрирования `ibcmd --pid=<pid>`: монопольного доступа нет, Apache и сервер
  не останавливаются; список файлов — относительные пути к `--base-dir`.
  Конфигуратор по `/S` на `/UpdateDBCfg` на автономном сервере рвёт сеанс
  (`recv returns zero`, ассерт `m_dbOperationsBlock`) — использовать `ibcmd`.
  Подробности — док потребителя (`docs/ai/dev-ib-ibsrv.md`).
- **`--force-sessions`** / **`--no-force-sessions`** — разрешить/запретить авто-retry
  `/UpdateDBCfg` при ошибке «обнаружены клиенты, работающие по HTTP». Env:
  `UPDATE_DB_FORCE_SESSIONS` (по умолчанию `true`).

После merge: `./load-changed-files.sh -U`. Стоп: `Загрузка пропущена; только
UpdateDB` при ненулевой дельте `conf/` — смотри exit 21, затем `-F -U`.
`LOAD_HIDE_FILES` в `.env` прячет битые типовые формы на время designer.

Подробности — skill `/load-changed-files` и docs потребителя.

## Защиты движка (ворктри / чужая грязь / параллельные загрузки)

Движок сам предупреждает об опасных запусках (одна dev-ИБ на всех, загрузки
централизованы). Три проверки выполняются одним блоком перед началом загрузки —
**после** `--help` и раннего выхода «нет файлов к загрузке».

Env-гейты (в `.env` потребителя):

- **`IB_LOAD_STRICT`** (по умолчанию `false`) — `true` делает проверки 1 и 2
  жёстким отказом (exit) вместо предупреждения;
- **`IB_LOAD_FROM_WORKTREE`** (по умолчанию `false`) — осознанное разрешение
  грузить из ворктри (гасит только проверку 1). Флаги принимают `true`/`1`.

1. **Запуск не из главного чекаута.** Главный ворктри — первая запись
   `git worktree list --porcelain`; текущий — `git rev-parse --show-toplevel`.
   Не совпало и нет `IB_LOAD_FROM_WORKTREE` → `WARN` (при `IB_LOAD_STRICT` —
   `ERROR` + `exit 21`): загрузка из ворктри подменит конфигурацию ИБ дампом
   этого ворктри. Нет git / отвязанный HEAD — тихо пропускается.
2. **Чужая незакоммиченная грязь `conf/` в других ворктри.** Обходит
   `git worktree list --porcelain` (кроме текущего) и смотрит
   `git -C <путь> status --porcelain -- conf/`; непусто → `WARN` с перечнем до
   10 путей. При `-F` (полная пересборка) с `IB_LOAD_STRICT` — `ERROR` + `exit 22`;
   частичная загрузка — только `WARN`. Ошибки `git` при обходе — best-effort.
3. **Похоже, загрузка уже идёт по НАШЕЙ ИБ.** Сужает по basename базы из
   `IB_CONNECTION` (Windows: `1cv8.exe` с `CONFIG` или `ibcmd.exe`; Linux:
   `pgrep -af "1cv8|ibcmd"`). Читающие подкоманды `ibcmd` (`list`/`export`/
   `dump`/`help`) исключаются — они не пишут. Путь ИБ не распознан — тихо
   пропускается. Найдено → `WARN` с PID; жёсткого отказа нет даже при
   `IB_LOAD_STRICT` (риск ложных срабатываний — открытый конфигуратор/клиент).

### Безопасная проверка защиты 3

Защита 3 ловит «параллельную загрузку» по имени процесса (`ibcmd.exe` /
`1cv8.exe CONFIG`), суженному по basename базы из `IB_CONNECTION`. Локальная
проверка легко залипает: фоновый «декой» (поддельный процесс-загрузчик) держит
пайпы инструмента, вызов висит (реальные случаи — 38 и 50 минут, сняты вручную).
Правила:

1. **Боевая база — под запретом.** В `-i`, в декое и в `--db-path` — только
   выдуманный путь (`C:\base\guard-fake-ib`). Настоящий
   `C:\!Pavl0\Работа\КПСР.new\кпср_unf2020.dev.dt` не должен встретиться ни разу:
   при промахе защиты движок реально зальёт дамп из ворктри в общую dev-ИБ.
2. **Всё — в «глухом коконе»**: тест в отдельном `.sh`, снаружи только `timeout`,
   файл лога и `tail`, чтобы пайпы инструмента не были задействованы:

   ```bash
   timeout 180 bash /tmp/guard-test.sh > /tmp/guard-test.out 2>&1 </dev/null
   echo "rc=$?"; tail -30 /tmp/guard-test.out
   ```

3. **Декой сам завершается и не читает stdin** (процесс с именем `ibcmd.exe`, в
   командной строке которого есть выдуманный путь). Если декой залипает — **бросай
   тест**, в отчёте честно: «вариант X не проверен / проверен иначе».
4. **После теста** — проверка «не осталось ли процессов» (`Get-CimInstance` по
   имени/пути) и явный kill.

Проверяемые кейсы: чужой процесс (`rt.dev.dt`) — предупреждения нет; наш
`ibcmd`/`1cv8 CONFIG` — есть; `ibcmd extension list`/`config export` — нет.

## Preflight поддержки объектов

При partial-загрузке `conf/` скрипт делает preflight объектов на поддержке
(`Ext/ParentConfigurations.bin`). `parent_config.py` резолвится по порядку:
`PARENT_CONFIG_PY` → `scripts/parent_config.py` потребителя → канон
`harness/tools/load-changed-files/parent_config.py` (kit). Если файла нет
нигде — preflight пропускается с `WARN`, загрузка продолжается. Альтернатива —
`-F` (full-resync без preflight).

Внутренний список `-listFile` пишется в `.tmp/changed_files.txt` и удаляется
при любом выходе (успех/ошибка), в корне репозитория артефакт не остаётся.
Рабочие `temp_*.txt` движка тоже снимаются на любом выходе (EXIT-trap), так что
`git status` потребителя остаётся чистым даже при падении `-U`.

## UpdateDB упёрся в HTTP-клиентов (вторая публикация ИБ)

Симптом в логе:

```text
ОШИБКА: Обновление основной конфигурации базы данных завершилось с ошибкой (код: 1)
ОШИБКА:   Динамическое обновление конфигурации БД невозможно:
           обнаружены клиенты, работающие по HTTP
```

Причина: ИБ публикует не одна служба Apache. Скрипт гасит только
`APACHE_SERVICE_NAME`, а вторая публикация (например, MCP на другом порту,
служба `Apache24-2`) продолжает держать HTTP-сеансы — поэтому
`/UpdateDBCfg` не может взять эксклюзивную блокировку. Остановка
`APACHE_SERVICE_NAME` не помогает: файлы уже загружены, не применён только
UpdateDB.

Рабочая команда (designer), проверено на 8.5.1.1302:

```bash
1cv8.exe CONFIG /F"C:/base/proj" /UpdateDBCfg -Dynamic- -SessionTerminate force /DisableStartupDialogs
```

Важно: `-SessionTerminate force` работает **только** вместе с `-Dynamic-`.
Без `-Dynamic-` платформа на динамическое/эксклюзивное обновление не идёт,
и ошибка по HTTP-клиентам повторяется.

Движок делает этот retry сам, если после `/UpdateDBCfg` в логе есть признак
HTTP-клиентов и разрешён гейт `UPDATE_DB_FORCE_SESSIONS` (или явный
`--force-sessions`). Сеансы завершаются принудительно — в лог пишется `WARN`,
что пользователи отключаются. На prod-хостах гейт выключайте
(`UPDATE_DB_FORCE_SESSIONS=false` / `--no-force-sessions`): тогда скрипт
упадёт с подсказкой, но никого молча не разорвёт. Без второй публикации
(и без HTTP-ошибки) поведение не меняется.

### ibcmd

Аналог есть: у `ibcmd infobase config apply` ключи `--dynamic=<auto|disable|prompt|force>`
и `--session-terminate=<disable|prompt|force>` (по умолчанию `auto` и `disable`).
Retry движка для ibcmd:

```bash
ibcmd infobase config apply ... --force --dynamic=disable --session-terminate=force
```

### Мультислужбовый Apache

На Windows движок перед UpdateDB предупреждает, если в системе запущены другие
службы `Apache24*`/`*httpd*` кроме `APACHE_SERVICE_NAME`: они тоже публикуют ИБ
и держат HTTP-сеансы. Консьюмерский `tools/os/apache.sh` управляет одной службой;
список `APACHE_SERVICE_NAMES` пока не поддержан (будущее расширение).

## Полная загрузка: флаки-спин и ретраи

Симптом: полная загрузка (`-F`, а также partial с `Configuration.xml`) **залипает** —
сначала минуты живого I/O, затем CPU ~100% при **нуле** I/O, файл ИБ не меняется,
`/Out` пуст. Это не ошибка и не занятость: **флаки-гонка платформы**, а не свойство
дампа или монополии (проверено 26.09.2026: одна и та же `conf/` на пустой ИБ —
1 спин из 6 прогонов; на базе с расширениями спинит чаще, до 4/4 на отдельных файлах).

Что делать:

- запускать под `timeout` и **повторять 2–3 раза** — повтор обычно проходит;
- «жив или спинит» проверяется счётчиками процесса
  (`Get-CimInstance Win32_Process` → `ReadOperationCount`/`WriteOperationCount`)
  и mtime файла ИБ: спин = счётчики не растут, CPU не падает;
- **двухшаговый обход**, если спинит конкретный файл (в потребителе так вело себя
  `Roles/*/Ext/Rights.xml` на базе с расширениями): полная загрузка из дампа **без**
  этого изменения → затем **частичная** загрузка этого файла
  (`--list-file` + `SKIP_CONFIGURATION_CACHE=true`).

## Кэш хешей conf: тихий пропуск файла

Скрипт ведёт манифест sha256 и пропускает файлы, чей хеш совпал с записанным.
Неверная запись манифеста **самоподдерживается**: файл пропускается, а
пост-обновление снова пишет его хеш — файл не загрузится уже никогда, а прогон
отчитается успехом. Лечение: `SKIP_CONFIGURATION_CACHE=true` (грузит перечисленное
без сверки с кэшем). Имена пропущенных файлов печатаются в логе
(`Кэш conf, пропущены: …`) — если правка не появилась в ИБ, смотри эту строку.

## Порядок элементов в Form.xml

Платформа читает `Form.xml` через XDTO со строгим порядком потомков (например,
в `InputField` сначала `DataPath`, потом `Title`). Нарушение порядка даёт
«Исключение XDTO при чтении файла» при partial-загрузке и **CPU-спин** при `-F`.
Штатный `form-validate` это **не** ловит (проверено 26.09.2026). Если у потребителя
есть свой корпус форм — полезен эмпирический чекер: для каждого типа родителя
считаем направление пар «A перед B» по всему `conf/` и ищем файлы, идущие против
сильного большинства.

## Чек-лист агента

1. Правки в git (`conf/`, `cfe.xml/`)? → без `--list-file`.
2. Не трогал `cfe.xml/` → `--no-extensions`.
3. `.env` настроен (`cp .env.example .env`).
4. Обычный load: `./load-changed-files.sh -U`. Merge + отставание ИБ: `-F -U`.
5. Не записывать маркер = текущий HEAD до успешной заливки файлов.
6. BSL/XML проверки до load — `/bsl-check`, `/xml-wellformed`.
