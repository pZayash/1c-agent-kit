# Стратегия логирования

Позитивная стратегия: когда логировать и как — при условии, что логирование явно
оправдано. Писать в журнал через **обёртку потребителя**, если есть; иначе
`ЗаписьЖурналаРегистрации`.

> **Граница.** Здесь — «когда и как логировать». Бан на пустые
> `Попытка/Исключение` — [code-standards.md](code-standards.md).
> Транзакционный контекст лога (запись переживает откат) —
> [locks-and-transactions.md](locks-and-transactions.md).
> Имена обёрток / префикс событий — в доке потребителя, если есть.

## 1. Обёртка vs сырой журнал

Если есть обёртка:

- принимает `ИнформацияОбОшибке()` и сама разворачивает
  `ПодробноеПредставлениеОшибки` (не `КраткоеПредставлениеОшибки` — роняет стек);
- желательно **транзакционно-независимая** запись (лог переживает откат);
- `Данные` = **ссылки**, не `Структура` — отбор по сущности в журнале.

## 2. Когда логировать

| Сценарий | Лог? | Примечание |
| --- | --- | --- |
| Интеграции — исходящий HTTP/SOAP/очередь | **Да** | endpoint, метод, статус, время, correlation id. |
| Интеграции — входящий webhook / регламентный обмен | **Да** | источник, размер, принято/отклонено, причина. |
| Фоновые задания (`ДлительныеОперации`, `РегламентныеЗадания`) | **Да** | старт/финиш, успех/провал, параметры. |
| Ошибки проведения (`ОбработкаПроведения` → `Отказ = Истина`) | **Да** | документ, причина. |
| Откат транзакции | **Да** | причина + ключ документа/операции. |
| Стандартный CRUD через UI | **Нет** | платформенный аудит достаточен. |
| Необработанное исключение во внешнем обработчике | **Да** | полное `ПодробноеПредставлениеОшибки`. |
| Trace/debug при разработке | **Нет** | отладчик; убрать до коммита. |

Правило: **логируй то, что нельзя восстановить позже**.

## 3. Нейминг событий

```text
<ПрефиксПотребителя>.<Модуль/Тема>.<Операция>
```

Префикс может добавлять обёртка автоматически — тогда в `ИмяСобытия` без него.

Суффикс исхода (`.Ошибка`/`.Старт`/`.Финиш`) — **опционален**. Уровень `Ошибка`
уже несёт исход. Для длинных циклов (старт/финиш фона) — добавляй ради хронологии.

## 4. Уровни важности

- **`Ошибка`** — операция провалена, нужен разбор.
- **`Информация`** — успешное бизнес-значимое событие (интеграция, фон, статус).
- `Предупреждение` — деградировавший успех (retry, fallback). `Примечание` — редко.

## 5. Логирование ошибок в `Попытка/Исключение`

Ошибка пишется **один раз** с полным описанием, затем перевыброс:

```1c
Попытка
    ВыполнитьИнтеграционныйЗапрос();
Исключение
    ОбёрткаЖурналаОшибка(
        "Интеграция.ОбменСCRM",
        ИнформацияОбОшибке(),
        СсылкаДокумента);
    ВызватьИсключение;
КонецПопытки;
```

- **`ИнформацияОбОшибке()`** как комментарий — не краткое представление.
- **Перевыброс после лога** на границе интеграции, если контракт не «глотать».
- **Не двойное логирование.** Внутренний уже писал `Ошибка` — внешний максимум
  `Предупреждение` без повторного дампа.
- **Ссылки в `Данные`** — не разыменовывай ссылку только ради payload.
