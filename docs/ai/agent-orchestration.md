# Оркестрация агентов: тред-оркестратор и дочерние треды

Роль **оркестратора агентов** — bb-тред, который принимает задачу оператора,
режет её на брифы, запускает дочерние треды и владеет **политикой ресурса**
(сколько детей, кто первый, кто в общую ИБ). Оркестратор **не пишет код
конфигурации**.

> **Работает только в bb.** Вся механика ниже — bb-специфичная: дочерние треды,
> `bb thread spawn/tell/archive`, уведомления родителю, окружения-ворктри, сторож.
> В другом харнессе (Cursor и т. п.) скиллы остаются **текстом роли**: правила
> (брифы, приёмка, границы, «одна ИБ — один загрузчик») соблюдать можно, но спавна,
> уведомлений и архивации там нет — команда `bb …` не выполнится. Не обещай
> «дочка отчитается» в среде без bb.

Скиллы: [orchestrator](../../cursor/skills/orchestrator/SKILL.md) (роль
оркестратора) и [orchestrated-child](../../cursor/skills/orchestrated-child/SKILL.md)
(роль дочки). Смежное: ревью и хэндофф — локальные треды `handoffs/`,
[git-workflow.md](git-workflow.md).

## Границы: kit / потребитель

В kit — роль, брифы, спавн, контроль, приёмка, механика bb. У потребителя —
общий ресурс (одна dev-ИБ) и правила изоляции/аренды, интеграции (мосты,
порталы), пути и бутстрап окружения.

## Роли

| Роль | Делает | Не делает |
| --- | --- | --- |
| **Оператор** | намерение и постановщик, приёмка (дифф, прогон, UI), мьют дочки | — |
| **Оркестратор** | брифы, спавн, политика ресурса, блокеры, приёмка (дифф и проверки), задание интегратору, отчёт | код `conf/`, сам мерж и загрузка |
| **Дочка** | работу по брифу (как — её решение), коммиты в ветке, отчёт | мерж, `push`, загрузка в ИБ, выход за бриф |
| **Дочка-интегратор** | мерж одобренных веток в основную, загрузка в dev-ИБ, проверка результата | решения о качестве, правки `conf/` кроме конфликтов, `push` без команды |

## Цикл

1. Принять задачу оператора; выяснить намерение и постановщика.
2. Собрать брифы (см. ниже) и проверить, что `main` — union: то, что уже
   лежит в ИБ, но не закоммичено, обязано быть в `main` до первой загрузки.
3. Спавнить дочки с брифом; держать политику ресурса.
4. Контролировать ход (уведомления bb + сторож); отвечать на блокеры.
5. Принять работу: дифф, проверки, прогон. Мерж и загрузку отдать
   дочке-интегратору (см. «Приёмка и мерж»), `push` — по команде оператора.
6. Отчитаться оператору; **архивировать завершённых дочек** (см. «Архивация
   завершённых дочек»); затыки и решения — в память (см. ниже).

## Брифы

Два разных формата, сводить не нужно:

| Формат | Где | Что задаёт |
| --- | --- | --- |
| `programmer-task.md` | `задания/…` | **задачу** дочке: намерение (постановщик обязателен), объём, границы, проверки |
| `executor-task.md` | `openspec/changes/…` | **контракт** для слабой модели: роль, стоп-зона, сниппеты, DoD |

Правила брифа:

- Обязательны **намерение и постановщик**. Остальное опционально.
- Бриф лежит в `задания/<id>-<slug>/` в корне репозитория потребителя и
  **трекнут в git** (иначе ссылки внутри брифа мертвы для дочки).
- Бриф — разумный минимум строк. Дробление — на оркестраторе; «как делать» —
  на дочке.
- Общий кусок обоих форматов — **границы и стоп-зона**: чужой ресурс (общая ИБ),
  тяжёлый XML, коммиты/мерж, файлы других агентов. Выносится общей вставкой.
- Ссылки — **только на трекнутое** (`задания/**`, `openspec/**`, `docs/**`,
  `memory/**`, `research/**`). Ссылка на нетрекнутый файл для дочки мертва:
  нужный фрагмент (диагностику, выдержку) **инлайнят в бриф**.
- В брифе не ссылаться на `.env`, `.mcp.json`, `tools/` не из git: дочка
  копирует их из основного чекаута по явному указанию в брифе.
- **Бриф = разрешение на коммиты.** Канон kit «коммит только с явного
  разрешения» и «staging только вручную» ([git-workflow.md](git-workflow.md))
  действует и здесь: разрешением служит сам факт выдачи брифа — дочка сама
  делает `git add` и коммиты **в своём worktree**; оркестратор мержит по приёмке.
  В общих и чужих рабочих копиях ни дочка, ни оркестратор staging без спроса не
  делают.
- **Первая строка финального сообщения — статус и просьба** («готово», «жду X»,
  «нужно решение по Y»), подробности ниже. Родитель видит только первые 4000
  символов уведомления (см. «контроль хода»), всё, что после — до него не
  доедет.

## Спавн дочки

```bash
bb thread spawn --project <projectId> --parent-self \
  --new-environment worktree --base-branch main \
  --title "<id> <тема>" --prompt-file задания/<id>-<slug>/programmer-task.md
```

- `<projectId>` — из окружения треда (`BB_PROJECT_ID`) или `bb status`.
- Флаги свыше этих нужны редко: `--model` — по умолчанию проекта; `--section` —
  без секции; `--visibility` — ребёнок **наследует** видимость родителя.
- Бриф идёт **целиком в промпт** (`--prompt-file`) **плюс** дополнение о
  взаимодействии с оркестратором. Отдельный скилл
  [orchestrated-child](../../cursor/skills/orchestrated-child/SKILL.md) дочке
  копировать не нужно: overlay kit линкует `harness/cursor/skills/*` в
  `.cursor/skills/` потребителя при `bootstrap-kit`.
- Модель дочки выбирает оркестратор; оператор может выдать ему свои указания.

### Окружение worktree

Worktree делает плагин окружений — это **только клон репозитория, без provision**.
В свежем worktree обычно нет:

- `.env`, `.mcp.json`, `conf/ConfigDumpInfo.xml` (gitignored);
- submodule kit (`harness/`) — иногда ещё и потому, что закреплённый коммит kit
  есть только локально у соседнего worktree («not our ref»);
- бинарей и каталогов, которых нет в git (`tools/bsl-check`, `tools/mcp-call`,
  дампы типовой конфигурации).

Дочка бутстрапит это сама по указанию в брифе. Общий рецепт «перенос локальных
файлов + подстановка путей» — у потребителя (шаблоны `.worktreeinclude` /
`.bb-env-setup.sh`), потому что bb читает их из репозитория потребителя.

## Контроль хода

Два независимых пути:

1. **Уведомления bb родителю**: `child-completed`, `child-failed`,
   `child-interrupted`, `child-needs-attention` (плюс `ownership-assigned` /
   `ownership-removed` при смене родителя). Completion приходит пакетом с
   задержкой ~2 с.

   Вывод дочки в уведомлении — **выжимка, не отчёт**: bb берёт **первые 4000
   символов** финального сообщения и дописывает `[... output truncated ...]`
   (в исходниках `CHILD_THREAD_TERMINAL_OUTPUT_EXCERPT_CHAR_LIMIT = 4_000`,
   `truncateChildThreadOutput` режет как `text.slice(0, retainedLength)`, то есть
   хвост **отбрасывается**). Просьба или статус, дописанные в конец большого
   отчёта, до родителя **не доезжают**: живой случай — дочка закончила «Жду
   сигнала…» после таблицы ранбука, оркестратор хвоста не увидел и счёл её
   работу завершённой. Отсюда два правила:

   - **оркестратор**: по каждому завершению читать полное финальное сообщение из
     треда дочки — `bb thread log <child> --limit 1 --format minimal`;
     уведомление — только сигнал «есть что смотреть»;
   - **дочка**: статус и просьба — в первой строке финального сообщения, подробности
     ниже (см. «брифы»).
2. **Сторож залипших дочек** — автоматизация: раз в N минут смотрит детей
   оркестратора и **пишет только при подозрении**. Механические признаки:
   активная дочка без событий дольше порога; долгоживущий процесс загрузки
   конфигурации (`1cv8.exe … CONFIG`, `ibcmd.exe`). Второй признак — из опыта
   потребителя: фоновая загрузка по событиям видна как «дочка активна», поэтому
   сторожат и по процессу, а не только по тишине (**наблюдение**, не гарантия
   платформы). Тихий тик = `skipped`, токенов 0.
   Решение «залип или нет» и перезапуск — за оркестратором, скрипт только детектит.

Реакция: `child-needs-attention` — разобрать вопрос и ответить (или поднять
оператору); `child-failed` — решить: retry, смена модели, переразбиение брифа,
эскалация. Решение всегда за оркестратором.

### Грабли рантайма автоматизаций

- `bb` в скрипте автоматизации искать вручную не нужно: плагин сам резолвит его
  и инжектит `BB_CLI` (плюс каталог в `PATH`); не нашёл — печатает
  `[bb] warning:`, но скрипт всё равно стартует. На части окружений резолв не
  срабатывает (проба на Windows-хосте давала пустой `BB_CLI`) — тогда работает
  явный путь через `--env-json`.
- `--script-file` **копируется** в хранилище автоматизаций: правка исходника без
  `automation update` не действует.
- Тихий тик **скриптовой** автоматизации — это exit 0 и пустой вывод; последняя
  строка `{"wakeAgent": false}` даёт тот же результат. Рассчитывать на «пустой
  stdout» надо осторожно: постскрипт плагина может дописать предупреждение в
  stdout.
- На Windows PowerShell звать только с `[Console]::OutputEncoding = UTF8`,
  иначе кириллица в отчёте ломается.

## Приёмка и мерж

- Дочка отчитывается: что сделано, что и чем проверено, что осталось, блокеры.
- Оркестратор смотрит дифф и прогоняет проверки на изменённых файлах
  (см. `check-changed.sh` у потребителя), при сомнении — ревью по
  [review-request](../../cursor/skills/review-request/SKILL.md) /
  [review](../../cursor/skills/review/SKILL.md).
- Оператор может **замьютить дочку** (отвязать от оркестратора) и работать с ней
  сам: посмотреть диффы, запустить приложение, прогнать UI-тест. Пока дочка у
  оператора, оркестратор о ней ничего не знает — вернуть её обязательно (см.
  «механика bb»).

### Мерж и загрузка — отдельной дочкой-интегратором

Оркестратор **не делает мерж и загрузку сам**: он спавнит дочку-интегратора
([integrator](../../cursor/skills/integrator/SKILL.md)) и **архивирует её после
успешного цикла**. Причины: техника (мерж + долгая загрузка с ретраями) съедает
контекст оркестратора и мешает ему вести остальные треды.

Задание интегратору: список одобренных веток/коммитов, что загружать (полная
пересборка или список файлов), что проверить после загрузки. В ответ — отчёт с
первой строкой-статусом; по нему оркестратор закрывает цикл.

Важно: **мерж в основную ветку должен быть сериализован** (одна дочка-интегратор на
цикл). Параллельные мержи в один чекаут дают конфликты и гонку за индекс.

`push` — только по явной команде оператора; интегратор его сам не делает.

## Архивация завершённых дочек

Завершённую работу оркестратор **архивирует**: иначе список тредов в UI пухнет и
в работе теряется то, что действительно в работе. `bb thread list` и
`bb thread count` **не показывают** архивные (фильтр — `--archived`), то есть
архив = «убрано из списка, но не удалено».

```bash
bb thread archive <child> --json     # или --self из самого треда
bb thread unarchive <child> --json   # если понадобилось вернуть
```

### Архивai только своих

Оркестратор архивирует **только свои дочки** — те, у которых
`parentThreadId` = его тред:

```bash
bb thread list --parent-thread "$BB_THREAD_ID" --json   # фильтруй archivedAt == null
```

**Чужие треды не трогать** — даже если они давно завершены и мешаются в списке: у
них свой оркестратор или сам оператор, а архивация их **остановит и снесёт их
окружение** (см. ниже). Своих же — архивировать обязательно, иначе список пухнет
именно ими.

### Тред, который ждёт человека, — не завершён

Перед архивацией проверь **последнее сообщение** дочки. Если она ждёт проверки или решения
— от оркестратора или от оператора («жду решения по…», «проверьте, пожалуйста»,
«осталось подтвердить…») — работа **не закончена** и архивировать её **нельзя**:
архивация **остановит тред** и снесёт его окружение (для ворктри — `git worktree remove --force`),
и возврат потребует `unarchive` плюс восстановления контекста у человека.

Признак готовности к архивации: работа забрана (смержена/загружена, коммиты fetch'нуты),
проверки пройдены **и никто не ждёт ответа от человека**. «Готово, но жду приёмки» — не готово.

Если выяснилось, что уже архивный тред ждёт человека — вернуть его
(`bb thread unarchive <id>`) и передать тому, кто проверяет.

### Что делает архивация (сверено с исходниками bb 0.43.x)

Архивация — **не только флажок в UI**. Она:

1. ставит `archivedAt` (тред уходит из списка и счётчика);
2. **останавливает текущий ход** треда;
3. **снимает окружение** (`sweepProviderEnvironment`) — для эксклюзивного ворктри
   это `git worktree remove --force` (плагин `environment-git-worktree`).

Из пункта 3 — два следствия, на которых легко потерять работу:

- **незакоммиченное в ворктри исчезнет** вместе с ним;
- **коммиты в submodule внутри ворктри исчезнут тоже**: git-dir сабмодуля лежит
  в `<главный>/.git/worktrees/<id>/modules/<имя>` (свой на каждый ворктри), и
  этот каталог уезжает вместе с ворктри. Живой случай: ветка kit у дочки жила
  **только** там — её забирали `git -C harness fetch <путь-ворктри>/harness
  <ветка>` до архивации. Ветки **проекта** из ворктри так не теряются (ссылки
  живут в общем `.git`), но смысл имеют только если их забрали.

Общее окружение (канонический чекаут) архивация **не сносит**, пока в нём есть
другие живые треды (проверка `environmentHasLiveThreads`). Поэтому архивировать
дочку, работавшую в общем чекауте, безопасно.

### Чек перед архивацией

Три команды — «забрана ли работа»:

```bash
W=<путь-ворктри-дочки>
git -C "$W" status --porcelain                # грязь: это не работа?
                                               # (часто служебный .gitignore от плагина)
git -C "$W" log --oneline main..HEAD           # коммиты проекта, которых нет в main
git -C "$W/harness" log --oneline origin/master..HEAD   # коммиты kit (их надо fetch'нуть)
```

Архивируем, когда работа смержена в `main` (или сознательно выброшена), в отчёте
не осталось незабранных коммитов, а грязь объяснима.

**Не архивировать**: активные треды (архивация их остановит), треды с незабранной
работой, **треды, ждущие проверки/решения человека** (оркестратора или оператора),
**чужие треды** (не твои дети), треды оператора. Архивация родителя стопит **всё
дерево** — см. «Механика bb» ниже.

## Модели и сбои

Выбор модели дочке и реакция на сбой — **решение оркестратора**, не автоматика.
Полезные рамки: дочка на сбое не молчит дольше порога (иначе её ловит сторож);
падение по лимиту провайдера (квота) — не «залипание», лечится сменой модели или
переносом остатка; повторяющийся затык — признак, что бриф недорезан.

**Деньги.** По умолчанию дочка садится на **самую дешёвую модель, которая тянет
задачу** («Экономная»). Дорогая модель — только если:

- это **ревью/архитектура** (вердикт обязан быть от модели **сильнее** той, что
  писала код), или
- есть **явное указание оператора**, или
- дешёвая уже показала, что не тянет (повторные ошибки, залипание) — и тогда причина
  повышения идёт в отчёт.

Живой случай потребителя: за день все дочки отработали на дорогой модели, хотя задачи
были простые — бюджет ушёл впустую. Дефолт проекта может быть привязан к квотируемой
модели, поэтому **модель задавай явно на спавне**.

Смена модели у существующей дочки — `bb thread update <id> --model <модель>`
(липкая настройка, работу не запускает и тред не будит); разовая —
`bb thread tell <id> … --model <модель>`.

## Контекст дочек: пороги компакции

У дочки ограничено окно контекста: чем оно полнее, тем хуже ответы и дороже тред.

- **Смотреть:** `bb thread context <id> --json` → `usage.usedTokens` / `usage.modelContextWindow`
  (значения оценочные, `estimated: true`).
- **Сжимать:** `bb thread compact <id>` — **только для idle/errored** треда (во время хода нельзя,
  значит делаем в паузах: дочка отчиталась и ждёт).
- **Обнулить:** `bb thread clear <id>` — контекст пустой, дальше нужен бриф целиком
  (для тредов-«одноразовых исполнителей»).

**Пороги (решение оператора, 29.09.2026):**

| Заполнение | Что делать |
| --- | --- |
| **≥ 85 %** | сжимать **обязательно** |
| **≥ 65 %** | сжимать **желательно**; оставить можно, только если в контексте есть что-то очень важное для текущей задачи |
| **≥ 40 %** | **можно** сжать, если задача в основном закончена и тред уходит на подобную задачу (особенно переиспользуемые — интеграторы) |
| **> 65 % у оркестратора** | оркестратор **себя не сжимает** — предупреждает оператора, сжимает он |

Практика:

- после компакции **не полагаться на память треда**: суть следующей задачи передавать брифом
  (файлы, коммиты, ожидания) — так же, как при новом спавне;
- **предупреждать оператора**, если заполнение любого треда (включая оркестратора) выше 65 %;
- компакция — штатное обслуживание, а не признак сбоя: у долгоживущих тредов (интегратор,
  исполнитель на серии задач) её планируют заранее, в естественных паузах.

## Общий ресурс (одна ИБ)

Если у нескольких агентов **одна** база:

- **Один загрузчик.** Загрузка `conf/` идёт **только из канонического чекаута**
  (основного, где работает интегратор) — не из ворктри агентов. Загрузка из ворктри
  делает конфигурацию ИБ равной дампу **этого** ворктри: чужие незакоммиченные
  объекты исчезают из метаданных.
- **Ворктри — для правок, не для загрузки.** Ворктри нужны, чтобы агенты не дрались
  за индекс и рабочие файлы (параллельные правки в одном чекауте дают конфликты и
  `index.lock`). Но загрузка из ворктри — запрещена.
- Загрузка — операция под эксклюзивным владением. Механизм (аренда/билет, TTL,
  диагностика, принудительный сброс) — у потребителя; в брифе даётся короткая
  памятка «как взять и когда просить».
- Этапы в брифе: **A** — всё, что не требует ИБ (метаданные, модули, макеты,
  статика), **B** — загрузка и прогон, только по явной команде оркестратора.
  Это общее правило, а не костыль под конкретный проект.
- **Стоп-линия**: пока в ИБ есть незакоммиченное (в любом ворктри), полная
  загрузка вытеснит это из метаданных. Сначала `main` = union.
- **Не параллелить загрузки**: замка нет, два прогона ломают состояние.
- **Кэш хешей и `ConfigDumpInfo.xml` живут в чекауте, а состояние — в базе.**
  Кэш ворктри «не знает», что реально загружено, и может пропустить файл, отчитавшись
  успехом (тихий пропуск); лечение — `SKIP_CONFIGURATION_CACHE=true`. Поэтому
  загрузка из канонического чекаута ещё и снижает расхождение кэша и базы.
- Полная загрузка может **залипнуть** (флаки платформы): запускать под `timeout` и
  повторять 2–3 раза. Подробности — [load-config-to-dev.md](load-config-to-dev.md).

## Память и уроки

Затык и найденное решение оркестратор **пишет в память проекта** (запись
`memory/`) — не только в чат. Это топливо для разбора уроков (если у потребителя
есть скилл `/evolve`) и последующей правки скиллов: без него «топ-3 грабель»
теряется вместе с контекстом треда.

## Механика bb: родитель и ребёнок

Сверено с исходниками bb 0.43.4; базовые факты — из живых экспериментов на
0.43.3. Поведение версионно-чувствительное: перед опорой на пункт — сверить с
`bb ... --help` и текущей версией.

- Родителя у существующего треда меняет только `bb thread update <id>
  --parent-thread <id>` / `--clear-parent-thread`. По умолчанию каждая смена —
  **реальный ход родителя** (`ownership-assigned` / `ownership-removed`);
  `--no-ownership-notice` делает репарент тихим. Уведомления родителю
  выключаются отдельно — `--parent-notifications muted|on` (есть в исходниках
  новее 0.43.4; есть ли флаг в вашем рантайме — `bb thread update --help`).
- Пока `parentThreadId = null`, ребёнок **никого не уведомляет** — ни о
  завершении, ни о блокере.
- `--lifecycle-owner-thread` — другая связь: задаётся только при создании,
  уведомлений родителю не шлёт, но архивируется и удаляется **каскадом** вместе
  с владельцем.
- Архивация родителя архивирует и **стопит всё дерево** — но только то, что
  связано с ним сейчас: owner-зависимых, детей по `parentThreadId` и скрытые
  треды-источники. Восстановление — поштучно. Удаление родителя обнуляет
  `parentThreadId` у детей.
- Ограничения: валидация родителя (не archived/deleted/цикл/сам себя), глубина
  иерархии ≤ 4. Если ребёнок спавнится **без своего окружения** (окружение
  резолвится в проектное по умолчанию), у родителя оно должно быть — иначе сбой
  «Parent thread is missing an environment». При `--new-environment worktree`
  (обычный случай) родителю стартовать заранее не нужно.

Об архивации как операции (что сносит, чек перед ней) — раздел «Архивация
завершённых дочек».

Рецепт «забрать дочку себе и вернуть»:

```bash
bb thread update <child> --clear-parent-thread --json    # parentThreadId: null
bb thread tell <child> "…"                               # работаем
bb thread update <child> --parent-thread <parent> --json # вернули
```

Проверка после каждого шага: `bb thread show <child> --json` (`parentThreadId`)
или `bb thread list --parent-thread <parent> --json`.

Риски: забыли шаг 3 — оркестратор ждёт тред, которого нет в детях; отвязанная
дочка **переживает** архивацию родителя сиротой, о которой никто не знает (каскад
идёт по текущим связям); возврат к архивному родителю невозможен без `unarchive`;
уведомление о завершении, отправленное в те же ~2 с, уедет старому родителю.

## Загрузка и содержательное ревью не идут параллельно

Если по изменению назначено **содержательное ревью** (доменное, архитектурное), загрузка в ИБ ставится
**после** вердикта. «Загрузим сейчас, ревью посмотрим параллельно» — ловушка: ревью может признать код
вредным, и тогда в базе уже лежит опасная версия.

Живой случай (01.10.2026, change `address-form-city-prefill-parser`): кодовый прогон по всей рабочей ИБ
показал, что парсер даёт верный город в 172 карточках, но ~25 портит (записывает мусор в поле «Город» при
открытии/закрытии карточки). Загрузка к моменту прихода СТОПа **уже применилась** (4 минуты от старта),
и «грязная» версия оказалась в dev-ИБ; лечится только повторной загрузкой исправленной версии.

Правила:
- приостанавливать загрузку **до** ревью, даже если исполнитель уже отчитался «готово к загрузке»;
- исключение — чисто формальное ревью (документация, комментарии) или случай, когда загрузка нужна самому
  ревьюеру для проверки;
- проверяя «успела ли загрузка», смотреть не только лог применителя: мерж в `main` делается раньше, а
  применение занимает считанные минуты, поэтому СТОП может опоздать даже при быстрой реакции.
