# LDD — проектирование логов на фазе спеки

Log-driven development: логи проектируются вместе с дизайном, до кода — не
«дописать потом». Секция «Логирование» в `design.md` фиксирует события, уровни,
поля и точки записи; реализация следует таблице, triage-прогон проверяет её
фактом прочитанных логов.

Практика из индустрии: обязательные логи/метрики/алерты уже в initial commit
(Logz.io); spec-first logging — события объявляются артефактом спецификации
(GitLab Artifact Registry, spec S03-a-logging).

> **Граница.** Здесь — стеко-нейтральный контракт проектирования. Runtime-правила
> «когда и как писать в журнал» — [logging-strategy.md](logging-strategy.md)
> (не рефакторить). Маппинг уровней и механика записи/чтения — в binding-доке
> стека `stacks/<s>/docs/ai/ldd-<s>.md`.

## 1. Секция «Логирование» в design.md

Обязательна, когда фича имеет логируемые границы: интеграции, фоновые задания,
обработчики ошибок, многошаговые сценарии. Шаблон:

```markdown
| Событие | Уровень | Поля/Данные | Точка | Когда |
| --- | --- | --- | --- | --- |
| order.submit | INFO | order_id, user_id, latency_ms | exit | успех |
| order.submit | ERROR | order_id, error | error | отказ |
```

- `Точка` — entry / exit / error / boundary (см. § 4).
- Поля, содержащие секреты или PII, помечать явно — см. redaction в § 4.
- Стековые детали (имя функции записи, объект журнала) в таблицу не вносить —
  это binding.

## 2. Нейминг событий

Dotted `<домен>.<операция>`: `order.submit`, `payment.reconcile`,
`sync.customers`. Суффикс исхода (`.start` / `.ok` / `.error`) — опционален:
уровень уже несёт исход. Для длинных операций суффиксы `.start`/`.ok` дают
хронологию — добавляй.

## 3. Уровни (generic)

| Generic | Смысл |
| --- | --- |
| ERROR | операция провалена, видна пользователю/вызывающему |
| WARN | успех через fallback/retry/деградацию |
| INFO | нормальный переход состояния, виден в проде |
| DEBUG | пошаговая деталь, выкл. по умолчанию |

Маппинг generic → уровни стека — в `stacks/<s>/docs/ai/ldd-<s>.md`.

## 4. Правила

- **Wide event** — один богатый event на операцию, а не лог шагов: «логируй что
  случилось с операцией, не что делает код». Для длинных операций — wide event
  на границе каждой стадии.
- **Log points** — entry/exit/error на каждой границе (HTTP, job, интеграция):
  entry = intent (входные ключи), exit = outcome + latency, error = stack +
  correlation.
- **Correlation id** обязателен в многошаговых сценариях — один id сквозь все
  события цепочки.
- **Запись переживает откат транзакции** где возможно — иначе лог падает вместе
  с операцией, которую должен был объяснить.
- **Redaction** — секреты/PII в спеке помечать явно; в логе — маска или отказ
  от поля.
- **Triage gate** — перед «готово» прочитать логи реального прогона и сверить с
  таблицей спеки. Механизм чтения — в stack binding.
- **Алерты/дашборд** — опционально, если у стека есть канал оповещения.
